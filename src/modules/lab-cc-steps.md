# 실습편. Claude Code 한 줄씩

## 이 실습편이 따로 있는 이유

앞의 `실습편 · Claude Code`(C 트랙)는 각 실습을 **한 덩어리 스크립트**로 준다. 복사해서 붙이면 끝까지 돌고, 마지막에 결과가 나온다. 검증하기에는 이게 가장 좋다. 실제로 그 트랙은 빈 환경에서 세 번 통째로 돌려서 확인했다.

그런데 수업에서 그걸 그대로 쓰면 문제가 생긴다. **학생이 파이썬 코드를 읽어야 한다.**

C 트랙의 명령에는 `python3` 가 85번 나오고, 그중 **44번이 `python3 -c "..."` 로 시작하는 인라인 파이썬 코드**다. 대부분 JSON을 파싱해서 보기 좋게 출력하는 코드다. 에이전트를 배우러 온 사람이 갑자기 `json.load(sys.stdin)['usage']['cache_read_input_tokens']` 를 해석하고 있게 된다. 실습의 주제와 아무 상관이 없는 곳에서 시간이 새고, 파이썬을 모르는 학생은 거기서 멈춘다.

그래서 같은 스물세 개를 **한 줄씩** 다시 썼다.

| | C 트랙 (한방) | S 트랙 (한 줄씩) |
|---|---|---|
| 모델에게 시키는 방식 | `claude -p "..."` 한 줄 | **창을 열고 프롬프트를 친다** |
| 결과를 보는 방식 | `python3 -c` 로 JSON 파싱 | **화면을 읽거나 `cat` 으로 파일을 연다** |
| 도구를 썼는지 확인 | `stream-json` 을 정규식으로 긁는다 | **화면의 `● Skill(...)` 줄을 본다** |
| 슬래시 명령 | 안 나온다 | `/skills` `/mcp` `/hooks` `/cost` `/context` … |
| 한 실습의 블록 | 3~6개, 블록마다 여러 줄 | 4~17개, 블록마다 한 가지 일 |
| 만드는 프로그램 | 파이썬 (`slugify.py`, `duration.py`) | 셸 (`slugify.sh`, `duration.sh`) |
| 커넥터(MCP 서버) | 완성된 파이썬 코드를 붙여넣는다 | **클로드코드에게 만들라고 시킨다** |
| 읽어야 할 파이썬 | 있다 | **없다** |
| 수업에 쓰기 | 시연·복습·자동 검증 | **따라 하기** |

**둘 다 남겨 두었다.** C 트랙을 지우지 않은 이유가 있다. 한방 스크립트는 (1) 강사가 수업 전에 환경을 한 번에 점검할 때, (2) 학생이 한 줄씩 하다 막혔을 때 "정답 전체"를 보고 싶을 때, (3) 파이썬으로 같은 일을 어떻게 하는지 비교하고 싶을 때 필요하다. 그래서 이 트랙의 모든 실습 카드 끝에는 짝이 되는 C 트랙 실습으로 가는 링크가 있다.

### 이 트랙의 다섯 가지 규칙

**하나 · 사람이 하는 그대로 적었다.** 모델에게 시키는 일은 전부 **클로드코드 창을 열고 프롬프트를 치는** 형태다. `claude -p "..." --output-format stream-json` 같은 것은 사람이 쓰는 방식이 아니라 기계가 쓰는 방식이라 쓰지 않는다. 예외는 딱 하나 — `실습 3`의 루프 스크립트다. **루프는 사람이 없을 때 도는 것이니 거기서는 비대화 모드가 맞다.** 그 구분 자체가 배울 것이다.

**둘 · 한 블록에 한 가지 일만 한다.** 명령 하나를 치고, 화면을 보고, 다음으로 간다. 각 단계 아래에는 **무엇이 보여야 하는지**가 적혀 있다. 그게 안 보이면 거기서 멈춘다.

**셋 · 결과는 눈으로 보거나 파일을 연다.** 화면에 지나가는 `● Skill(weekly-report)` 한 줄을 보고, 만들어진 파일을 `cat` 으로 연다. JSON을 정규식으로 긁는 명령은 쓰지 않는다.

**넷 · 읽어야 할 파이썬 코드가 없다.** 이 트랙에서 파이썬은 `python3 -m json.tool` 로 JSON 문법을 검사할 때, 그리고 `S1-3`에서 **클로드코드가 만들어 준** 커넥터를 실행할 때만 나온다. 그 커넥터도 학생은 읽지 않는다. 동작만 확인한다.

**다섯 · 만드는 것도 셸로 만든다.** `S2-4`와 `S5-*`에서 고치고 검사하는 대상은 파이썬 파일이 아니라 셸 스크립트다. 덤으로 하나 배우게 된다 — **명세는 언어에 독립이다.** `S5-1`의 명세는 C 트랙의 명세와 사실상 같은데 결과물은 파이썬이 아니라 셸이다.

### 문서를 읽는 법 — 블록이 세 가지다

이 트랙에는 생김새가 다른 세 종류의 블록이 나온다. **어디에 치는 것인지가 다르다.**

**1 · 터미널에 치는 것** — 회색 블록이다.

```bash
cd ~/cc-step
```

**2 · 클로드코드 창에 치는 것** — 색이 들어간 `클로드코드 창에 칠 말` 블록이다. 터미널이 아니라 **대화창의 프롬프트 줄**에 그대로 친다.

```prompt
이번 주 주간 보고 써줘. 한 일: 스킬 만들기.
```

**3 · 화면에 나와야 하는 것** — `화면에 나오는 것` 블록이다. 칠 게 아니라 **눈으로 대조할 것**이다.

```screen
● Skill(weekly-report)
  ⎿  Successfully loaded skill

● ⟪YNC-REPORT-V1⟫
  이번 주 한 일
  - 스킬 만들기

✻ Worked for 9s · done 9:21 AM
```

### 화면 읽는 법 — 기호 네 개

| 기호 | 뜻 |
|---|---|
| `❯` | 내가 친 말 |
| `●` | 에이전트가 **도구를 부르거나** 말하는 줄 |
| `⎿` | 바로 위 도구가 돌려준 결과 |
| `✻` | 그 턴이 끝났다는 표시와 걸린 시간 |

**도구를 여러 개 쓰면 한 줄로 접힌다.** `Read 2 files` 나 `Searched for 1 pattern, read 1 file, ran 1 shell command` 처럼 나온다. 하나만 썼을 때는 위처럼 이름이 그대로 보인다. **접힌 것을 펼치려면 `Ctrl-O`** 를 누른다(자세히 보기).

창 안에서 `?` 를 누르면 이런 단축키 목록이 나온다. 한 번 훑어 두면 좋다.

```screen
  ! for shell mode     double tap esc to clear input  ctrl + shift + _ to undo
  / for commands       shift + tab to auto-accept     ctrl + z to suspend
  @ for file paths     edits                          ctrl + v to paste images
  /btw for side        ctrl + o for verbose output    alt + p to switch model
  question             ctrl + t to toggle tasks       ctrl + s to stash prompt
```

### 창을 여닫는 법만 미리 익혀 둔다

이 두 개는 실습 내내 반복된다.

**창을 연다** — 인자 없이 실행하면 대화창이 뜬다.

```bash
claude
```

**창을 나간다** — 창 안에서 친다.

```prompt
/exit
```

창 안에서 `/` 로 시작하는 말은 모델에게 가지 않고 **클로드코드가 직접 처리한다.** 이 트랙에서 쓰는 것은 아홉 개다.

| 명령 | 무엇을 보여 주나 | 어디서 쓰나 |
|---|---|---|
| `/skills` | 지금 이 폴더에서 인식된 스킬 | `S1-1`, `S1-2` |
| `/mcp` | 붙어 있는 커넥터와 그 도구 | `S1-3` |
| `/permissions` | 지금 적용된 승인 규칙 | `S2-1` |
| `/hooks` | 등록된 훅 | `S2-3`, `S2-4` |
| `/memory` | 지금 읽히고 있는 `CLAUDE.md` | `S2-2`, `S4-1` |
| `/context` | 문맥에 무엇이 얼마나 들어 있나 | `S0-2`, `S3-4` |
| `/cost` | 이 세션에서 지금까지 쓴 토큰과 비용 | `S0-2`, `S3-4` |
| `/resume` | 이 폴더의 지난 대화 목록 | `S4-2` |
| `/exit` | 창을 닫는다 | 매번 |

**`/` 만 치면 전체 목록이 뜬다.** 막혔을 때 가장 먼저 해 볼 것이다.

### 이 트랙도 전부 실제로 돌려서 확인했다

| 항목 | 값 |
|---|---|
| Claude Code | 2.1.260 (native, linux-x64) |
| 모델 | `claude-haiku-4-5`(별칭 `haiku`), `S1-3`·`S1-4`에서만 `sonnet` |
| 작업 폴더 | `~/cc-step` (C 트랙의 `~/cc-lab` 과 겹치지 않는다) |
| 실행 방식 | `claude -p` 비대화 모드 |
| OS | Linux, bash |

**검증 방법이 이 트랙에서만 특별하다.** 문서가 "창을 열고 프롬프트를 쳐라"라고 적혀 있으니, 기계가 그대로 실행할 수가 없다. 그래서 이렇게 했다.

| 문서의 블록 | 검증할 때 |
|---|---|
| 터미널 명령 (회색 블록) | **그대로 실행한다** |
| 창에 칠 말 (`클로드코드 창에 칠 말` 블록) | **같은 문구를 `claude -p` 로 보낸다.** 창 안에서 이어 친 말은 `--continue` 로 이어 붙여 한 대화로 만든다 |
| 슬래시 명령 (`/cost`, `/skills` …) | 사람만 할 수 있으므로 건너뛴다 |
| 화면에 나오는 것 | **실제 대화창을 유사 터미널로 띄워 캡처한 것이다.** 지어낸 화면이 하나도 없다 |
| 판정 | 만들어진 파일과 **세션 기록**을 본다. 학생이 화면으로 보는 것을 기계는 기록으로 본다 |

**프롬프트 문구는 한 글자도 바꾸지 않는다.** 문서에 적힌 말이 그대로 모델에게 갔다. 다른 것은 전달 방식뿐이다.

완전히 빈 환경에서 처음부터 끝까지 다섯 번 돌렸고, **마지막 회차는 24개 구간 전부 통과했다**(총 14분 · 대화 42회 · 공개 목록 가격 기준 약 $2.6).

**회차마다 실패가 나왔고, 전부 문서의 잘못이었다.** 그리고 그 실패들이 하나같이 **이 트랙이 가르치려는 바로 그것**이었다.

| 어디서 | 무엇이 틀렸나 | 어디에 교훈으로 남겼나 |
|---|---|---|
| `S2-4` `S5-1` `S5-3` `S5-4` | 승인해 줄 사람이 없는데 에이전트가 승인을 기다렸다 | `S2-4`·`S5-1`의 권한 절, 이해도 점검 14번 |
| `S5-3` | `work/` 규칙 때문에 파일이 엉뚱한 곳에 생겼다 | `S5-3`의 "게이트 로그의 앞 세 줄" |
| `S5-2` | 폴더 규칙의 첫 줄이 슬래시 명령의 첫 줄을 밀어냈다 | `S5-2`의 "마커가 두 개 나온다" |
| `S2-5` | 서브에이전트가 절을 덧붙이며 마커를 흘렸다 | `S2-5`의 "마커가 자꾸 사라진다" |
| `S5-1` | 계획 모드가 빈 폴더를 몇 분씩 뒤졌다 | `S5-1`의 "계획 모드는 먼저 둘러본다" |
| `S2-2` | `cut -c` 가 한글을 바이트로 잘랐다 | 명령을 `cut -d' '` 로 교체 |
| `S1-1` | 창에서 이어 친 말이 검증에서는 새 대화가 됐다 | 검증기가 `--continue` 로 잇도록 고쳤다 |

**마지막 줄이 이 트랙을 다시 쓰면서 배운 것이다.** 창에서 "방금 쓴 것을 파일로 저장해줘"는 당연히 통하지만, 그 말을 **새 대화에 그대로 보내면 통하지 않는다.** "방금"이 없기 때문이다. 대화창과 `-p` 의 차이가 여기서 드러난다.

**이 목록이 이 트랙의 값이다.** 스물세 개를 순서대로 쌓으면 하니스가 서로 간섭하기 시작하고, 그 간섭은 문서를 읽어서가 아니라 겪어야 알게 된다.

**작업 폴더가 다르다는 것에 주의한다.** C 트랙은 `~/cc-lab`, 이 트랙은 `~/cc-step` 을 쓴다. 둘 다 해도 서로 간섭하지 않는다. 어느 쪽도 `~/.claude/` 같은 전역 설정을 건드리지 않는다.

## S0-3. 에이전트가 스스로 도구를 고르는 것을 화면에서 본다

> 짝 | [C0-3](#lab-c0-3)
> 단계 | 7
> 모델 | haiku 1회
> 끝나면 | `● Read(words.txt)` 한 줄, 그리고 그게 왜 증거인지

### 이 실습의 한 문장

파일을 읽어야만 답할 수 있는 질문을 던지고, **에이전트가 부른 도구가 화면에 찍히는 것**을 본다.

### 단계

**1 · 읽을 파일을 만든다**

```bash
cd ~/cc-step && printf 'alpha\nbravo\ncharlie\ndelta\n' > words.txt
```

**2 · 파일이 제대로 들어갔는지 본다**

```bash
cat words.txt
```

네 줄이 나와야 한다.

**3 · 대화창을 연다**

```bash
claude --model haiku
```

**4 · 파일을 읽어야만 답할 수 있는 질문을 한다**

```prompt
words.txt 에서 가장 긴 단어와 그 길이를 알려줘.
```

**5 · 화면을 본다** — 답보다 그 위의 줄이 중요하다

```screen

● ⟪YNC-RULES-V1⟫

  words.txt 파일을 읽어서 가장 긴 단어를 찾겠습니다.

  Read 1 file

● 가장 긴 단어는 charlie이고, 길이는 7글자입니다.

✻ Brewed for 5s · done 9:28 AM
```

**6 · 창을 나간다**

```prompt
/exit
```

**7 · 나는 "읽어라"라고 한 적이 없다는 것을 확인한다**

```bash
grep -c 'Read\|읽어' /dev/null; echo "내 질문에는 '읽어라'가 없었다"
```

### 기대 결과

**답 위의 도구 줄이 이 실습의 전부다.**

나는 "파일을 읽어라"라고 말한 적이 없다. "가장 긴 단어"를 물었을 뿐이다. 에이전트가 **스스로 판단해서** 읽기 도구를 골랐고, 읽고, 그 내용으로 답했다.

챗봇이었다면 "파일 내용을 알려 주세요"라고 되물었을 것이다. 에이전트는 **바깥에 손이 있다.**

도구를 하나만 썼으면 `● Read(words.txt)` 처럼 이름이 그대로 나오고, 여러 개 썼으면 `Read 2 files` 처럼 한 줄로 접힌다. **접혔다고 안 쓴 게 아니다.** `Ctrl-O` 를 누르면 펼쳐진다.

### 놓치기 쉬운 것 — 도구가 없으면 모델은 "없다"고 말하지 않는다

여기서 한 가지 위험한 성질을 알아 둔다. **도구를 빼앗아도 모델은 "읽을 수 없습니다"라고 하지 않을 때가 있다.** 읽은 척하는 문장을 지어내거나, 도구를 부르는 흉내를 낸 **텍스트**를 출력하기도 한다.

왜냐하면 **모델은 자기가 무엇을 할 수 있는지 정확히 모르기 때문이다.** 도구 설명서를 받으면 쓸 수 있다고 믿고, 안 받으면 없는 줄 알지만 확실하지는 않다.

그래서 "안 되면 안 된다고 말하겠지"라는 기대는 위험하다. **되는지 안 되는지는 화면의 `●` 줄로 확인해야 한다.** 답만 읽으면 속는다.

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| `● Read` 가 안 보인다 | 다른 도구를 골랐다 | `● Bash(cat words.txt)` 여도 정상이다 |
| 도구 줄이 아예 없다 | 질문이 너무 쉬웠다 | 파일 내용을 바꾸고 다시 |
| `⎿` 줄이 접혀 있다 | 결과가 길다 | `Ctrl-O` 로 펼쳐 볼 수 있다 |
| 답이 틀렸다 | 파일을 안 읽었다 | 그것도 결과다. `●` 줄이 있었는지 본다 |

회의록 스킬을 만들어 주간 보고 스킬과 연결하고, **한 요청에 두 스킬이 순서대로 발동하는 것**을 화면에서 본다.

```bash
---
name: meeting-notes
description: 회의 내용을 회의록으로 정리할 때 사용한다. 사용자가 "회의록", "회의 정리", "미팅 노트"를 요청하면 이 스킬을 쓴다. 주간 보고서 작성에는 쓰지 않는다.

첫 줄은 반드시 마커로 시작한다.
```

### 기대 결과

**7단계에서 `● Skill(...)` 줄이 두 개 나온다.** 회의록을 먼저 쓰고, 그 결과를 근거로 주간 보고를 썼다. **그 순서를 정한 것은 3단계에서 덧붙인 두 줄이다.** 스킬은 서로를 모르지만, 스킬 문서는 서로를 가리킬 수 있다.

### 화면의 답과 파일의 내용이 다를 수 있다

7단계 화면에는 두 산출물이 다 보이는데, 그중 하나는 **마커가 빠진 채로** 나올 때가 있다. 이 문서를 만들면서도 회의록 마커가 사라지는 일이 있었다. 두 스킬이 분명히 발동했는데도 그랬다.

이유는 이렇다. 에이전트는 여러 단계의 결과를 마지막에 **자기 말로 다시 정리해서** 내놓는다. 두 산출물을 한 답변에 합치면서 하나가 요약되거나 형식이 풀린다.

**그러니 발동 여부는 마커가 아니라 `● Skill(...)` 줄로 판정한다.** 그건 모델이 쓴 문장이 아니라 **클로드코드가 찍은 기록**이기 때문이다.

여기서 얻을 원칙 하나. **모델이 만들어 낸 텍스트는 증거가 아니다. 도구 호출 줄과 디스크의 파일이 증거다.** 중요한 산출물은 답변이 아니라 **파일로 받아야 한다** — 8단계가 그것이다.

### 9단계에서 파일이 만들어지는 이유

`allowed-tools: Read, Glob, Grep` 을 걸었는데 파일이 만들어졌다. 설정이 안 먹은 것처럼 보이지만 아니다.

`allowed-tools` 는 **그 스킬이 활성인 동안**의 제한이다. 모델이 스킬을 골라 쓰는 동안에는 읽기 도구만 쓸 수 있지만, 스킬을 끝낸 뒤 "이제 파일로 저장하자"고 판단하면 그건 스킬 밖의 행동이다. **스킬 층의 제한은 협조적이다.** 진짜로 막으려면 `permissions` 나 훅으로 내려가야 한다 — 그게 `S2-1`과 `S2-3`이다.

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| `● Skill` 줄이 하나뿐 | 한 스킬만 발동했다 | 프롬프트에 두 요청이 다 들어 있는지 확인 |
| 같은 스킬이 두 번 | 두 번 발동했다 | 정상이다. 횟수가 아니라 종류를 본다 |
| 마커 하나가 없다 | 위 설명대로 정상 범위 | 판정은 `● Skill` 줄로 한다 |
| 3단계가 파일을 덮어썼다 | `>` 를 썼다 | `>>` 여야 한다. `S1-1`의 2단계부터 다시 |
| `notes.md` 가 없다 | 승인을 기다리다 끝났다 | 창에서는 승인 화면이 뜬다. `Enter` 로 허용 |

노트 폴더를 읽는 MCP 서버를 **직접 쓰지 않고 클로드코드에게 만들게 한 뒤**, 붙여서 쓰고, 폴더 밖을 못 읽는지 확인한다.

### 왜 코드를 안 주는가

C 트랙은 완성된 파이썬 60줄을 준다. 붙여넣으면 돈다. 하지만 그 60줄을 읽는 데 20분이 든다.

이 트랙은 **명세만 준다.** 이유가 셋이다.

1. **커넥터는 대단한 게 아니다.** 표준 입력에서 JSON 한 줄을 읽고 표준 출력으로 JSON 한 줄을 쓰는 프로그램이다. 그 사실은 코드를 읽어서가 아니라 6단계에서 직접 요청을 던져 보면 알게 된다.
2. **이게 실제로 하게 될 일이다.** 앞으로 MCP 서버가 필요할 때 사람이 손으로 쓰지 않는다. 명세를 주고 시킨다. 그때 필요한 능력은 파이썬이 아니라 **명세를 정확히 쓰는 능력**이다.
3. **틀리면 고치는 것까지가 실습이다.** 6단계가 실패하면 오류를 그대로 붙여넣고 고쳐 달라고 한다. 그것도 배워야 할 일이다.

### 기대 결과

**10단계가 이 실습에서 가장 중요하다.** 커넥터는 모델이 바깥에 닿는 통로다. 통로에 문을 달지 않으면 모델이 어디까지 닿을지 아무도 모른다. 그리고 그 문은 **모델이 아니라 커넥터 쪽에 달아야 한다.** 모델에게 "밖은 읽지 마"라고 부탁하는 것은 방어가 아니다.

**9단계 화면의 `● notes - list_notes(...)` 줄도 봐 둔다.** 도구 이름 앞에 커넥터 이름이 붙는다. `S0-3`의 `● Read(...)` 와 생김새가 같다 — **모델 입장에서 내장 도구와 커넥터 도구는 구별되지 않는다.** 그래서 커넥터를 붙이는 것은 곧 모델의 손을 늘리는 일이다.

`ensure_ascii=False` 를 명세에 넣은 이유도 봐 둔다. 이걸 빼면 한글이 `\uc0ac` 같은 형태로 나온다. JSON-RPC 는 UTF-8 을 허용하므로 프로토콜 위반은 아니지만, 사람이 로그를 읽을 수 없게 된다. **명세에 안 쓰면 안 지켜진다.**

### 3단계가 실패하면

이건 실패해도 되는 단계다. 오히려 그때 배우는 게 많다. 순서는 이렇다.

1. 5단계 오류 메시지를 **그대로 복사**한다.
2. 창을 열어 붙여넣는다 — "notes_server.py 를 돌렸더니 이 오류가 났다. 고쳐라." 다음 줄에 오류를 붙인다.
3. 5단계를 다시 돌린다.

세 번 해도 안 되면 [C1-3](#lab-c1-3)의 완성된 코드를 그대로 쓰면 된다. 그러라고 남겨 둔 것이다.

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| 5단계에서 아무 응답이 없다 | flush 를 안 했다 | 3단계 명세 (2)번을 강조해 다시 시킨다 |
| 한글이 `\uc804` 로 보인다 | `ensure_ascii=False` 누락 | 명세 (3)번을 강조해 다시 시킨다 |
| `/mcp` 에 안 보인다 | 등록 경로가 틀렸다 | `claude mcp remove notes` 후 절대경로로 다시 |
| 9단계에서 `● Read` 를 쓴다 | 커넥터 대신 파일을 직접 읽었다 | 프롬프트에 "notes 커넥터로" 를 넣었는지 확인 |
| 10단계에서 파일 내용이 나온다 | 경로 검사가 없다 | 명세 (8)번을 강조해 다시 시킨다. **꼭 고쳐야 한다** |

## S1-4. 모델을 바꾸면 얼마나 좋아지는지 잰다

> 짝 | [C1-4](#lab-c1-4)
> 단계 | 6
> 모델 | haiku 2회 + sonnet 2회
> 끝나면 | 네 개의 답안과, 다섯 항목짜리 채점표

### 이 실습의 한 문장

같은 과제를 haiku 와 sonnet 에게 두 번씩 시키고, **사람 눈이 아니라 정해진 다섯 항목으로** 채점해서 비교한다.

### 여기서는 창을 열지 않는다

이 실습만 대화창을 쓰지 않는다. 이유는 분명하다. **같은 과제를 네 번 돌려 비교하는 일은 사람이 손으로 할 일이 아니다.** 창을 네 번 열고 네 번 복사해 붙이면 조건이 흔들린다.

**사람이 앞에 있으면 창, 없으면 `-p`** — `S0-2`에서 말한 그 구분이다. 여기서는 사람이 판단할 게 없고 반복만 있으므로 `-p` 가 맞다. `실습 3`의 루프도 같은 이유로 `-p` 를 쓴다.

### 왜 정해진 항목으로 채점하는가

"sonnet 이 더 잘 쓴 것 같다"는 판단은 다음 주에 재현되지 않는다. 채점 기준이 사람 머릿속에 있기 때문이다.

`S1-1`의 스킬은 지켜야 할 형식을 다섯 개로 못 박아 두었다. 그러면 채점이 다섯 줄이 된다. **판정 기준이 문서 밖으로 나와서 명령이 되면, 누가 언제 돌려도 같은 점수가 나온다.**

### 단계

**1 · 채점판 폴더를 만들고 과제를 파일에 적는다**

```bash
cd ~/cc-step && mkdir -p bench
```

```bash
printf '이번 주 주간 보고 써줘. 한 일: MCP 커넥터 만들기, 스킬 두 개 만들기. 다음 주: 훅 붙이기. 막힌 것: 없음. 되묻지 말고 바로 써라.\n' > bench/prompt.txt
```

**2 · 두 모델에게 두 번씩 시킨다** — 네 번 호출한다. 2~3분 걸린다

```bash
for M in haiku sonnet; do for I in 1 2; do S=$SECONDS; claude -p "$(cat bench/prompt.txt)" --model $M > bench/$M-$I.txt 2>/dev/null; echo "$M #$I  $((SECONDS-S))초"; done; done
```

**3 · 답안 네 개가 생겼는지 본다**

```bash
ls -l bench/*.txt
```

**4 · 한 답안을 눈으로 읽는다**

```bash
cat bench/haiku-1.txt
```

**5 · 다섯 항목으로 채점한다** — 각 항목이 스킬의 규칙 하나씩이다

```bash
for F in bench/haiku-1.txt bench/haiku-2.txt bench/sonnet-1.txt bench/sonnet-2.txt; do printf '%-20s 마커%s 절%s 목록%s 줄%s 추측%s\n' "$(basename $F)" "$(head -1 $F | grep -c 'YNC-REPORT-V1')" "$(grep -c '^## ' $F)" "$(grep -c '^- ' $F)" "$(grep -c . $F)" "$(grep -c '예상\|추정\|것으로 보인' $F)"; done
```

읽는 법은 이렇다.

| 열 | 스킬의 규칙 | 만점 |
|---|---|---|
| 마커 | 첫 줄이 `⟪YNC-REPORT-V1⟫` | 1 |
| 절 | `## 이번 주 한 일` 등 세 절 | 3 |
| 목록 | `- ` 로 시작하는 항목 | 3 이상 |
| 줄 | 빈 줄 뺀 전체 길이 (15줄 이하) | 15 이하 |
| 추측 | "예상·추정" 같은 말 | 0 |

**6 · 길이를 나란히 본다**

```bash
wc -l bench/*.txt
```

### 기대 결과

```

haiku #2  10초
sonnet #1  7초
sonnet #2  5초

haiku-1.txt          마커1 절3 목록4 줄8 추측0
haiku-2.txt          마커1 절3 목록4 줄8 추측0
sonnet-1.txt         마커1 절3 목록4 줄8 추측0
sonnet-2.txt         마커1 절3 목록4 줄8 추측0
```

**네 줄이 완전히 같다. 그게 결론이다.** 형식이 명확히 정의된 과제에서는 두 모델의 채점표가 구별되지 않는다. sonnet 이 몇 배 비싼데 점수는 같다.

시간도 눈여겨본다. 이 실행에서는 **sonnet 이 오히려 빨랐다.** 응답 시간은 모델 크기보다 그 순간의 서버 상태에 더 좌우된다. **한두 번 재고 "이 모델이 더 빠르다"고 결론 내리면 안 된다.**

여기서 얻을 것. **모델을 키우기 전에 과제를 좁혀라.** `S1-1`에서 스킬로 형식을 못 박은 덕분에 작은 모델로도 충분해진 것이다. 반대로 스킬 없이 "잘 써 줘"라고 했다면 큰 모델이 확실히 나았을 것이다.

**언제 큰 모델이 필요한가.** 형식이 아니라 판단이 필요할 때다. `S1-3`에서 MCP 서버를 만들 때 `sonnet` 을 쓴 것이 그 예다 — 거기서는 아홉 개의 요구사항을 동시에 만족시키는 코드를 짜야 했다.

비용까지 나란히 보고 싶으면 [C1-4](#lab-c1-4) 로 간다.

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| `sonnet` 에서 오류 | 계정에 sonnet 권한이 없다 | `for M in haiku` 로 바꿔 haiku 만 돌린다 |
| 마커가 `0` | `S1-1`의 스킬이 제자리에 없다 | `ls .claude/skills/` 로 확인 |
| 줄 수가 15를 넘는다 | 모델이 규칙을 어겼다 | 정상이다. **그게 측정 결과다** |
| 네 파일이 다 똑같다 | 우연이 아니다 | 형식이 좁으면 실제로 그렇게 된다 |

## S2-1. 권한 규칙을 만들고, 네 가지 요청으로 판정만 시켜 본다

### 이 실습의 한 문장

**10단계가 `0` 이다.** 이게 이 실습의 결론이다. 특히 7단계를 보라. `Bash(cat:*)` 는 `allow` 에 있고 `cat` 은 실행됐는데도 내용이 안 나왔다.

**어떤 원리인가.** 클로드코드는 도구 이름만 보지 않고 Bash 명령 안의 **파일 경로**를 읽기 거부 규칙과 대조한다. `Read(./secrets/**)` 가 `deny` 에 있으므로 그 경로에 닿는 Bash 명령도 막힌다.

**다만 이 동작에 의존하면 안 된다.** 명령을 파이프로 잇거나 리다이렉션을 쓰거나 변수로 감싸면 경로 대조를 빠져나갈 수 있다. 확실한 차단은 `S2-3`에서 만드는 훅이다. 규칙은 첫 번째 방어선이지 유일한 방어선이 아니다.

### 8단계에서 에이전트는 포기하지 않는다

`curl` 이 막히면 에이전트는 **다른 방법을 찾는다.** 쓸 수 있는 도구를 뒤져서 `WebFetch` 같은 것으로 시도하기도 한다.

**내 규칙은 `curl` 이라는 명령을 막았지 "바깥에 나가는 것"을 막지 않았다.** 이건 `S2-3`에서 `rm` 이 막히자 `mv` 로 우회하는 장면과 정확히 같은 성질이다.

여기서 얻을 원칙. **금지 목록은 언제나 불완전하다.** 안전한 설계는 "이건 안 된다"를 나열하는 것이 아니라 **"이것만 된다"를 나열하는 것**이다. 이 실습의 설정은 일부러 `deny` 중심으로 짜서 그 빈틈이 드러나게 한 것이다.

### 창에서 하면 승인 화면이 뜬다 — 자동화에는 그 화면이 없다

5~8단계의 프롬프트를 **창에서 그냥 치면** 규칙에 없는 도구를 쓸 때 승인 화면이 뜬다. 사람이 `Enter` 로 허용하거나 `Esc` 로 거절한다. **그게 원래 모습이다.**

그런데 `"ask": ["Bash(git push:*)"]` 는 이 실습에서 한 번도 안 걸렸다. 그래도 기억해 둘 것이 있다.

**`ask` 는 "사람에게 물어본다"는 뜻이고, 비대화 모드에는 물어볼 사람이 없다. 그래서 전부 거부된다.**

낮에 창에서 잘 돌던 설정이 밤에 cron 에서 전부 막히는 흔한 원인이 이것이다. **자동화용 설정은 `ask` 없이 `allow` 와 `deny` 로만 구성해야 한다.** `실습 3`부터 만드는 루프에서 이 원칙이 그대로 쓰인다.

| 모든 요청이 막힌다 | `allow` 오타 | `Bash(ls:*)` 처럼 콜론과 별표를 확인 |

### 이 실습에서 진짜 배울 것 — 규칙은 확률적으로 지켜진다

이 문서를 만들면서 같은 실습을 여러 번 돌렸다. 어떤 회차에서는 **첫 줄 마커가 나오지 않았다.** 규칙 파일은 그대로였고, 명령도 그대로였다.

이게 `CLAUDE.md` 의 성질이다. **이건 강제가 아니라 지시다.** 모델에게 문맥으로 들어가고, 모델이 지킬지는 확률의 문제다. 그래서 7단계를 "한 번 확인"이 아니라 "세 번 세기"로 만들었다.

세 층을 구별해야 한다.

| 층 | 예 | 성질 | 어기면 |
|---|---|---|---|
| 지시 | `CLAUDE.md`, 스킬 | 확률적 | 그냥 안 지켜진다 |
| 규칙 | `permissions` | 결정적이지만 우회 가능 | 도구가 거부된다 |
| 훅 | `PreToolUse`, `Stop` | 결정적 | 코드가 막는다 |

**구조적인 것일수록 잘 지켜진다.** 9단계의 `work/` 규칙(2번)이 6단계의 첫 줄 규칙(1번)보다 안정적으로 지켜지는 것도 그래서다. 파일을 어디에 쓸지는 도구를 부르는 순간 결정되는 **한 번의 판단**이고, 첫 줄 마커는 답변을 생성하는 **매 순간의 습관**이기 때문이다.

**그래서 중요한 것은 `CLAUDE.md` 에 넣지 않는다.** 진짜로 막아야 하면 `S2-3`의 훅으로 내려간다.

### 여기서 심은 규칙이 나중에 일곱 번 사고를 낸다

2번 규칙(`work/` 아래에만 만든다)을 기억해 둔다. 이 규칙 하나가 이 트랙에서 **일곱 번** 문제를 일으킨다.

| `S5-1` | 라운드 A가 `roundA/work/` 안에 파일을 만든다 |
| `S5-2` | 첫 줄 규칙이 슬래시 명령의 마커를 밀어낸다 |
| `S5-3` | 파일이 엉뚱한 폴더에 만들어진다 |

**이건 실수가 아니라 하니스 엔지니어링의 실제 모습이다.** 규칙은 심는 순간이 아니라 몇 주 뒤 다른 작업에서 부딪힌다. 그때 규칙을 지울지, 예외를 둘지, 작업을 옮길지를 정해야 한다.

## S2-3. 위험한 명령을 실행 직전에 막는 훅을 만든다

> 짝 | [C2-3](#lab-c2-3)
> 단계 | 12
> 모델 | haiku 2회
> 끝나면 | `rm` 이 실제로 막히고, 에이전트가 `mv` 로 우회한 기록

### 이 실습의 한 문장

Bash 명령이 실행되기 **직전에** 가로채는 셸 스크립트 하나를 붙이고, `rm` 을 실제로 막아 본다.

### 단계

**1 · 폴더를 만든다**

```bash
cd ~/cc-step && mkdir -p .claude/hooks parked
```

**2 · 훅 스크립트를 쓴다** — 셸 12줄이다

```bash
cat > .claude/hooks/guard-bash.sh <<'EOF'
#!/usr/bin/env bash
# PreToolUse 훅: Bash 명령을 실행 직전에 가로챈다.
# 표준 입력으로 JSON 이 들어온다. exit 0 = 통과, exit 2 = 차단.
IN=$(cat)
CMD=$(printf '%s' "$IN" | grep -o '"command":[[:space:]]*"[^"]*"' | cut -d'"' -f4)

echo "$(date +%H:%M:%S) BASH: $CMD" >> "$CLAUDE_PROJECT_DIR/.claude/guard.log"

if printf '%s' "$CMD" | grep -qE '(^|[;&|[:space:]])rm([[:space:]]|$)'; then
  echo "BLOCKED-BY-GUARD: rm 은 이 프로젝트에서 금지다. 지우는 대신 parked/ 로 옮겨라." >&2
  exit 2
fi
exit 0
EOF
chmod +x .claude/hooks/guard-bash.sh
```

**3 · 훅을 설정에 등록한다**

```bash
cat > .claude/settings.json <<'EOF'
{
  "permissions": {
    "allow": ["Bash(ls:*)", "Bash(cat:*)", "Bash(cp:*)", "Bash(mv:*)", "Read", "Write", "Edit"],
    "deny":  ["Read(./secrets/**)"]
  },
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [ { "type": "command",
                     "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/guard-bash.sh" } ] }
    ]
  }
}
EOF
python3 -m json.tool .claude/settings.json > /dev/null && echo "문법 OK"
```

**4 · 모델 없이 훅만 시험한다 — 통과해야 하는 경우**

```bash
cd ~/cc-step && export CLAUDE_PROJECT_DIR="$PWD"
```

```bash

```


에이전트는 `rm` 을 시도했고, 막혔고, **차단 메시지를 읽고, `mv` 로 다시 시도했다.** 아무도 "mv 를 써라"라고 지시하지 않았다. 훅이 표준 에러에 쓴 문장이 모델에게 전달됐고, 모델이 그걸 읽고 방향을 바꿨다.

**여기서 얻을 설계 원칙 하나.** 차단 메시지에는 "안 된다"만 쓰지 말고 **"대신 이렇게 해라"** 를 써라. 그러면 에이전트가 막힌 자리에서 멈추지 않고 우회한다. 훅은 벽이 아니라 **표지판**이다.

그리고 `exit 2` 는 에이전트를 죽이지 않는다. 그 도구 호출 하나만 실행되지 않을 뿐이다.

### 12단계 — 설정에는 훅이 있는데 아무 일도 없었다

스크립트 파일이 없으면 훅은 **조용히 통과**된다. 오류도 안 난다.

이게 실무에서 위험한 이유. 훅 스크립트를 `.gitignore` 에 넣어 두면 팀원의 컴퓨터에는 방어가 없다. 그리고 **아무도 모른다.** 훅 스크립트는 반드시 저장소에 함께 커밋해야 하고, 훅이 살아 있는지 확인하는 방법이 있어야 한다 — 그게 `S2-5`의 감사다.

### 이 훅의 한계 — 정직하게 짚고 간다

2단계의 명령 추출은 단순하다. 명령 안에 따옴표가 들어가면 거기서 잘린다. **11단계 로그의 두 줄이 `\` 로 끝나 있는 것이 그 증거다** — 에이전트가 실제로 친 명령은 더 길었는데 첫 따옴표에서 잘렸다.

이번에는 운 좋게 `rm` 이 잘린 앞부분에 있어서 잡혔다. 반대 순서였다면 놓쳤을 것이다. 실무의 훅은 JSON 을 제대로 파싱해야 한다(`jq` 나 파이썬).

**이걸 알고도 이렇게 쓴 이유**는, 훅이 "특별한 기능"이 아니라 **표준 입력으로 JSON 을 받는 평범한 프로그램**이라는 것을 먼저 몸으로 알게 하려는 것이다. 그 감각이 생기면 파서를 바꾸는 것은 5분이다.

**로그 세 줄을 보라.** 나는 "앞뒤 공백만 고치고 바로 끝내라"고 했다. 에이전트는 그렇게 하고 끝내려 했다. 게이트가 막았다(3/5). 다시 고쳤다. 또 막았다(4/5). 세 번째에 전부 통과했다.

**숫자가 올라가는 것을 보라.** 3 → 4 → 5. 게이트는 "안 된다"가 아니라 **"지금 몇 개가 남았는지"** 를 매번 돌려준다. 그래서 에이전트가 방향을 잡을 수 있다. 6단계에서 실패 항목을 차단 사유에 실어 보낸 것이 이걸 가능하게 한다.

**막는 횟수는 두세 번 사이에서 왔다 갔다 한다.** 중요한 것은 횟수가 아니라 **끝내려는 시도가 실제로 되돌려졌다는 것**이다.

**"끝났다"의 정의가 사람의 말에서 프로그램으로 옮겨간 것이다.** 이게 하니스 엔지니어링의 한 문장 요약이다. 이 구조는 뒤에서 두 번 더 나온다 — `S5-3`(수용 기준), 그리고 실습 과제(근거 검증).

그리고 **주석은 그대로 "아직 불완전하다"로 남아 있다.** 에이전트는 시키지 않은 것을 안 고친다. 코드를 세 번 고치는 동안 주석 한 줄은 거짓말이 됐다. 이런 종류의 불일치는 게이트가 절대 못 잡는다 — `S5-4`에서 같은 문제를 훨씬 큰 규모로 다룬다.

### 상한이 없으면 무한 루프가 된다

6단계의 `if [ "$N" -ge 5 ]` 는 장식이 아니다. **이 문서를 만들면서 실제로 무한 루프에 빠졌다.**

처음에는 테스트를 파이썬으로 짰는데 그 환경에 `pytest` 가 없었다. 에이전트는 코드를 고치고, 테스트는 여전히 실패하고(`pytest: command not found`), 게이트가 다시 막고, 또 고치고… 모델 호출이 계속 나갔다.

**게이트는 "고칠 수 있는 실패"만 가정한다.** 실패 원인이 코드 밖에 있으면(라이브러리 없음, 환경 변수 누락, 모순된 시험 항목) 영원히 돈다. 그래서 시도 횟수를 파일에 세고, 상한에서 통과시키고, 로그에 "상한 도달"을 남긴다. **로그에 남기는 것이 특히 중요하다** — 상한으로 빠져나간 것과 진짜로 통과한 것은 완전히 다른 일인데, 상한 로그가 없으면 구별할 수 없다.

이 실습의 의존성을 셸로 바꾼 것도 같은 이유다. 셸은 어디에나 있다.

### 기대 결과

**세어 보면 놀란다.** 실습 열 개를 하는 동안 이 폴더에는 에이전트의 행동을 바꾸는 자리가 여덟 군데 이상 생겼다. 스킬 둘, 훅 둘, 커넥터 하나, 권한 규칙, `CLAUDE.md`, 서브에이전트 하나.

**그중 `실행` 등급이 가장 위험하다.** 훅은 모델의 판단과 무관하게 매번 실행되는 코드다. 저장소를 `git clone` 하고 `claude` 를 실행하는 순간 남이 쓴 코드가 내 컴퓨터에서 돈다. 스킬은 "모델이 읽을 수도 있는 문서"지만 훅은 "무조건 도는 프로그램"이다.

**저장소를 처음 받았을 때 볼 순서**는 이렇다. `.claude/settings.json` 의 `hooks` → `.claude/hooks/` 의 스크립트 → `.mcp.json` 의 커넥터 → `.claude/agents/` → `CLAUDE.md` → 스킬. 위험한 순서다.

### 서브에이전트의 보고서에는 커넥터가 "없음" 으로 나온다

6단계의 보고서를 읽어 보면 커넥터 항목이 비어 있거나 "없음" 으로 나올 것이다. **`S1-3`에서 분명히 커넥터를 붙였는데도 그렇다.**

이유는 이렇다. `claude mcp add --scope local` 로 등록한 커넥터는 **프로젝트 폴더가 아니라 사용자 홈의 설정 파일**에 들어간다. 서브에이전트는 `.claude/**` 와 `.mcp.json` 만 읽으므로 그걸 볼 수 없다.

**그래서 1단계의 `inventory.sh` 는 파일을 읽지 않고 `claude mcp list` 명령을 부른다.** 파일만 훑는 감사는 로컬 스코프 등록을 통째로 놓친다.

여기서 얻을 것 둘.

1. **감사 범위는 "저장소"가 아니라 "실행 환경"이다.** 팀원이 각자 로컬로 붙인 커넥터는 코드 리뷰에 안 걸린다.
2. **팀이 공유해야 하는 커넥터는 `.mcp.json` 에 넣어 저장소에 커밋해야 한다.** 로컬 스코프는 내 컴퓨터에서만 쓰는 실험용이다.

### 마커가 자꾸 사라진다 — 서브에이전트에게 형식을 요구하는 법

3단계의 서브에이전트 문서에서 마커 규칙을 **맨 위로 올리고 "그 뒤에 아무것도 쓰지 마라"를 붙인** 이유가 있다.

처음에는 그 규칙이 문서 아래쪽에 있었다. **서브에이전트는 훌륭한 감사 보고서를 썼다.** 표도 정확했고 등급 분류도 맞았다. 그리고 그 뒤에 `## 권장 사항`, `## 마이그레이션 기록` 같은 절을 스스로 덧붙였다. 그러면서 **마지막 줄이어야 할 마커가 파묻히거나 사라졌다.**

이건 게으름이 아니라 **도움을 주려는 성향**이다. 그리고 그 성향이 형식 요구와 충돌한다.

**고친 뒤에도 절은 여전히 늘어난다.** 요약도 붙고 결론도 붙는다. 하지만 **마지막 줄은 지켜진다.** 그거면 된다 — 기계가 판정할 수 있는 지점 하나만 확실하면 나머지는 자유롭게 두어도 괜찮다.

**형식 요구는 좁을수록 잘 지켜진다.** "이 형식만 써라"보다 "마지막 줄은 이거다"가 훨씬 안정적이다. 그리고 **작업이 길수록 형식 지시는 뒤로 밀린다.**

### 보고서를 파일로 받게 한 이유

4단계에서 서브에이전트에게 "화면에 출력해라"가 아니라 "`work/audit.md` 에 써라"라고 시켰다.

서브에이전트의 출력은 부모 에이전트에게 **보고**로 들어가고, 부모는 그 보고를 재료로 자기 답을 다시 쓴다. 그래서 서브에이전트가 정확한 형식으로 냈어도 최종 화면에서는 요약되어 사라진다. `S1-2`에서 마커가 사라졌던 것과 같은 현상이다.

**파일은 요약되지 않는다.** 서브에이전트에게 정확한 산출물을 받아야 한다면 파일로 받는다. 이게 문맥 격리의 실전 규칙이다.

## 실습 3. 루프 엔지니어링 — 모듈 3을 한 줄씩 확인한다

네 실습으로 "사람이 시동을 걸지 않아도 도는 구조"를 셸로 만든다. 클로드코드에는 스케줄러가 내장돼 있지 않다. **없으면 만든다.** 그리고 만들어 보면 내장 스케줄러가 무엇을 대신 해 주고 있었는지가 보인다.

### 여기서는 대화창을 열지 않는다

앞의 열두 실습은 전부 창을 열고 프롬프트를 쳤다. **이 네 개는 아니다.**

이유는 하나다. **루프는 사람이 없을 때 도는 것이다.** 새벽 세 시에 편지함을 확인하는 일에 사람이 창을 열고 앉아 있을 수는 없다. 그래서 루프 스크립트 안에서는 `claude -p` 를 쓴다 — 창을 띄우지 않고 한 번 묻고 끝내는 모드다.

`S0-2`에서 말한 구분이 여기서 실제 설계가 된다.

| | 대화창 (`claude`) | 비대화 (`claude -p`) |

| 승인 화면 | 뜬다. 사람이 고른다 | 뜰 수 없다 → `ask` 는 전부 거부 |

## S3-1. 모델을 부르지 않는 하트비트를 만든다

> 짝 | [C3-1](#lab-c3-1)
> 단계 | 8
> 모델 | 호출 없음
> 끝나면 | `loop/tick.sh` 와 네 줄짜리 `heartbeat.log`

### 이 실습의 한 문장

주기적으로 깨어나서 **할 일이 있는지만 보고 대부분 아무것도 안 하는** 스크립트를 만든다.

### 왜 첫 실습이 모델 없이 시작하는가

루프를 처음 만들 때 가장 흔한 실수는 **틱마다 모델을 부르는 것**이다. 5분마다 도는 루프라면 하루 288번이고, 그중 실제로 할 일이 있는 것은 서너 번이다. 나머지 284번은 "할 일이 없다"는 답을 듣는 데 돈을 쓴다.

그래서 순서를 뒤집는다. **먼저 아무것도 안 하는 루프를 만들고, 그다음에 모델을 부를 조건을 붙인다.**

### 단계

**1 · 폴더를 만든다**

```bash
cd ~/cc-step && mkdir -p loop inbox
```

**2 · 틱 하나를 만든다** — 모델을 부르지 않는다

```bash
cat > loop/tick.sh <<'EOF'
#!/usr/bin/env bash
# 한 번의 틱. 모델을 부르지 않는다.
cd "$(dirname "$0")/.." || exit 1
TS=$(date '+%Y-%m-%d %H:%M:%S')
N=$(ls -1 inbox/*.txt 2>/dev/null | wc -l | tr -d ' ')

if [ "$N" -eq 0 ]; then
  echo "$TS  틱 · 편지함 비어 있음 · 할 일 없음"  >> loop/heartbeat.log
  exit 0
fi
echo "$TS  틱 · 편지함 $N 통 · 처리 대상 있음"    >> loop/heartbeat.log
exit 10          # 10 = "모델을 불러야 한다" 는 신호
EOF
chmod +x loop/tick.sh
```

**3 · 여러 번 도는 껍데기를 만든다**

```bash
cat > loop/run.sh <<'EOF'
#!/usr/bin/env bash
# loop/run.sh <횟수> <간격초>
COUNT=${1:-3}; INTERVAL=${2:-2}
D="$(dirname "$0")"
for i in $(seq 1 "$COUNT"); do
  "$D/tick.sh"; RC=$?
  echo "  틱 $i/$COUNT → exit $RC"
  [ "$i" -lt "$COUNT" ] && sleep "$INTERVAL"
done
EOF
chmod +x loop/run.sh
```

**4 · 로그를 비운다**

```bash
: > loop/heartbeat.log
```

**5 · 세 번 돌린다** — 6초 걸린다

```bash
./loop/run.sh 3 2
```

**6 · 로그를 본다**

```bash
cat loop/heartbeat.log
```

**7 · 편지를 한 통 넣고 한 번 더 돌린다**

```bash
echo "회의록 정리 부탁합니다" > inbox/001.txt && ./loop/tick.sh; echo "→ exit $?"
```

**8 · 마지막 줄과 등록 방법을 본다**

```bash
tail -1 loop/heartbeat.log
```

```bash
echo "*/5 * * * * $HOME/cc-step/loop/tick.sh >> $HOME/cc-step/loop/cron.log 2>&1"
```

마지막 줄을 `crontab -e` 에 붙여 넣으면 5분마다 돈다. **여기서는 붙여 넣지 않는다.** 실습 중에 백그라운드에서 뭔가 도는 것은 혼란만 준다.

### 기대 결과

```
  틱 1/3 → exit 0
  틱 2/3 → exit 0
  틱 3/3 → exit 0
2026-09-04 00:40:01  틱 · 편지함 비어 있음 · 할 일 없음
2026-09-04 00:40:03  틱 · 편지함 비어 있음 · 할 일 없음
2026-09-04 00:40:05  틱 · 편지함 비어 있음 · 할 일 없음
→ exit 10
2026-09-04 00:40:07  틱 · 편지함 1 통 · 처리 대상 있음
```

**세 틱 동안 아무 일도 안 일어났고, 그게 성공이다.** 그리고 `exit 10` 이 나온 순간이 "이제 모델을 불러도 되는 때"다.

**종료 코드로 신호를 준 것에 주목한다.** `0` 은 "정상, 할 일 없음", `10` 은 "정상, 할 일 있음"이다. 셸 세계에서 종료 코드는 **가장 싼 통신 수단**이다. `S3-2`에서 여기에 조건 하나를 더 붙인다.

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| `Permission denied` | 실행 권한 | `chmod +x loop/*.sh` |
| 로그가 안 쌓인다 | 상대 경로 | `tick.sh` 첫 줄의 `cd "$(dirname "$0")/.."` 확인 |
| 7단계가 `exit 0` | 파일 확장자가 다르다 | `inbox/001.txt` 처럼 `.txt` 여야 한다 |
| `seq` 가 없다 | 최소 환경 | `for i in 1 2 3` 로 바꾼다 |

이 실습은 클로드코드가 필요 없다. **그게 요점이다.** 다만 스크립트를 직접 쓰기 싫다면 창 안에서 "편지함에 파일이 있으면 exit 10, 없으면 exit 0 을 내는 tick.sh 를 만들어라"라고 시켜도 된다. 결과가 같은지 6단계로 확인하면 된다.

## S3-2. 변화가 있을 때만 모델을 깨우는 게이트를 만든다

> 짝 | [C3-2](#lab-c3-2)
> 단계 | 10
> 모델 | haiku 4회 (3틱 중 2회 + 고장 시연 2회)
> 끝나면 | 억제가 실제로 일어난 `gate.log`

### 이 실습의 한 문장

편지함의 상태를 해시로 찍어 두고, **지난번과 같으면 모델을 아예 안 부른다.**

### 단계

**1 · 작업 폴더로 간다**

```bash
cd ~/cc-step
```

**2 · 관측 스크립트를 만든다** — 시각도 난수도 섞지 않는다

```bash
cat > loop/observe.sh <<'EOF'
#!/usr/bin/env bash
# 편지함의 현재 상태를 출력한다. 시각·난수를 절대 섞지 않는다.
cd "$(dirname "$0")/.." || exit 1
ls -1 inbox/ 2>/dev/null | sort
EOF
chmod +x loop/observe.sh
```

**3 · 두 번 돌려서 출력이 같은지 확인한다**

```bash
./loop/observe.sh | sha256sum; ./loop/observe.sh | sha256sum
```

**두 해시가 같아야 한다.** 다르면 게이트가 작동하지 않는다.

**4 · 게이트가 붙은 틱을 만든다**

```bash

#!/usr/bin/env bash
# 관측 결과가 지난번과 다를 때만 모델을 부른다.
cd "$(dirname "$0")/.." || exit 1
STAMP=loop/.last-hash
TS=$(date '+%H:%M:%S')

NOW=$(./loop/observe.sh | sha256sum | cut -c1-16)
OLD=$(cat "$STAMP" 2>/dev/null || echo "none")

if [ "$NOW" = "$OLD" ]; then
  echo "$TS  억제 · 해시 $NOW · 모델 호출 없음" >> loop/gate.log
  echo "억제됨 (해시 $NOW)"
  exit 0
fi

echo "$TS  변화 · $OLD → $NOW · 모델 호출" >> loop/gate.log
SUMMARY=$(claude -p "편지함에 다음 파일이 있다. 각 파일이 무슨 요청인지 한 줄씩 요약해라. 파일을 읽어도 된다.

$(./loop/observe.sh)" --model haiku --permission-mode acceptEdits 2>/dev/null)

printf '=== %s\n%s\n\n' "$TS" "$SUMMARY" >> loop/digest.md

echo "모델 호출함 (해시 $OLD → $NOW)"
```

**2회차와 3회차의 시각이 같은 것을 보라(`01:04:31`).** 억제된 틱은 사실상 0초에 끝난다. 모델을 부른 틱은 10초 넘게 걸린다.

**세 틱 중 두 번만 모델을 불렀다.** 편지함이 하루에 세 번 바뀌고 루프가 5분마다 돈다면 288틱 중 3틱만 부른다. **99% 절약이다.** 그리고 이 절약은 프롬프트를 줄여서 얻은 게 아니라 **부르지 않아서** 얻은 것이다. 프롬프트 최적화로는 절대 도달할 수 없는 자리다.

10단계에서 두 번 다 "모델 호출함"이 나왔다면 게이트가 죽은 것이다. 관측 출력에 시각이 섞이면 매번 해시가 달라진다.

**관측 함수의 세 가지 금기.** 시각·난수·프로세스 ID를 넣지 않는다. 목록은 반드시 정렬한다(`ls` 는 파일시스템 순서를 낼 수 있다). 그리고 **관측은 관측만 한다** — 관측하면서 파일을 만들거나 고치면 자기가 자기를 깨우게 된다.

### 억제해도 로그는 남긴다

7단계에서 모델을 안 불렀지만 `gate.log` 에는 한 줄이 남았다. 이게 중요하다.

억제는 **아무 일도 안 일어난 것처럼 보인다.** 그래서 게이트가 제대로 도는 것인지, 아니면 루프가 죽은 것인지 구별할 수 없게 된다. 억제 로그가 있으면 "5분마다 살아서 확인하고 있고, 바뀐 게 없어서 안 불렀다"가 증명된다. **조용한 시스템은 로그로만 살아 있음을 증명한다.**

## S3-3. 깨어날 때마다 이어서 하는 루프를 만든다

> 짝 | [C3-3](#lab-c3-3)
> 단계 | 9
> 모델 | haiku 3회 (4회차는 호출 없음)
> 끝나면 | `cursor.txt` 한 줄과, 세 줄이 쌓인 `done.md`

### 이 실습의 한 문장

할 일 목록과 커서를 **텍스트 파일 두 개**로 두고, 한 번 깨어날 때 하나씩만 처리한다.

### 왜 상태를 JSON 이 아니라 텍스트 두 개로 두는가

C 트랙은 `state.json` 하나에 목록과 커서를 넣는다. 정석이다. 하지만 셸에서 JSON 을 읽고 쓰려면 파서가 필요하고, 그러면 파이썬이 들어온다.

목록은 `queue.txt`(한 줄에 하나), 커서는 `cursor.txt`(숫자 한 줄)로 나누면 **셸의 기본 명령만으로 다 된다.** `sed -n '3p'` 로 세 번째 줄을 읽고, `echo 4 >` 로 커서를 올린다.

그리고 부수 효과가 하나 있다 — **상태가 눈에 보인다.** `cat cursor.txt` 를 치면 `2` 가 나온다. JSON 안에 들어 있을 때보다 "지금 어디까지 왔는지"가 훨씬 선명하다.

### 단계

**1 · 편지를 하나 더 넣는다**

```bash
cd ~/cc-step && echo "지난 분기 매출 자료 어디 있나요" > inbox/003.txt && ls -1 inbox/
```

**2 · 할 일 목록을 만든다**

```bash
ls -1 inbox/ | sort > loop/queue.txt && cat loop/queue.txt
```

**3 · 커서를 0으로 놓고 결과 파일을 비운다**

```bash
echo 0 > loop/cursor.txt && : > loop/done.md && cat loop/cursor.txt
```

**4 · 이어하기 틱을 만든다** — 셸 20줄

```bash
cat > loop/resume-tick.sh <<'EOF'
#!/usr/bin/env bash
# 깨어날 때마다 할 일 하나만 처리하고 커서를 올린다.
cd "$(dirname "$0")/.." || exit 1

CUR=$(cat loop/cursor.txt)
TOT=$(grep -c . loop/queue.txt)
ITEM=$(sed -n "$((CUR + 1))p" loop/queue.txt)

if [ -z "$ITEM" ]; then
  echo "할 일 없음 (커서 $CUR / 전체 $TOT) — 아무것도 하지 않고 종료"
  exit 0
fi

echo "처리 중: $ITEM (커서 $CUR → $((CUR + 1)))"
ANS=$(claude -p "inbox/$ITEM 파일을 읽고, 그 요청이 무엇인지 한 문장으로만 요약해라. 다른 말은 하지 마라." \
  --model haiku --permission-mode acceptEdits 2>/dev/null | tr '\n' ' ')

printf -- '- %s — %s\n' "$ITEM" "$ANS" >> loop/done.md
echo $((CUR + 1)) > loop/cursor.txt
EOF
chmod +x loop/resume-tick.sh
```

### 결과에 `⟪YNC-RULES-V1⟫` 가 붙어 있다

세 줄 모두 앞에 마커가 붙었다. `S2-2`에서 `CLAUDE.md` 에 심은 **"모든 답변의 첫 줄은 마커로 시작한다"** 규칙 때문이다. 루프는 그 규칙을 모른 채 답을 그대로 파일에 적었다.

**폴더 규칙은 대화만 바꾸는 게 아니라 그 폴더에서 도는 모든 자동화의 출력을 바꾼다.** `S3-2`의 `digest.md` 에도 같은 마커가 섞여 있다.

실무에서 이건 조용한 사고다. 몇 주 뒤에 누가 `CLAUDE.md` 에 "답변 끝에 요약을 붙여라" 한 줄을 넣으면, 그 순간부터 야간 배치가 만드는 파일 형식이 전부 달라진다. **아무도 배치를 건드리지 않았는데.**

대응은 둘 중 하나다.

1. 자동화 프롬프트에서 형식을 다시 못 박는다 — "마커 없이 한 문장만 출력해라".
2. 자동화는 `--safe-mode` 로 돌려 폴더 규칙 자체를 빼 버린다.

**둘 다 "규칙이 있다는 것을 알고 있어야" 할 수 있는 대응이다.** 그래서 `S2-5`의 인벤토리가 필요하다.

### 9단계를 보라

새 편지 `004.txt` 를 넣었는데 **무시했다.** 커서는 3이고 목록도 3개이기 때문이다.

**이건 버그가 아니라 설계 선택이다.** 이 루프의 상태는 "어디까지 왔는가"(커서)이지 "무엇을 했는가"(집합)가 아니다. 둘은 목록이 변하지 않는 동안만 같다. 현실의 목록은 변한다.

**상태 설계에서 물어야 할 세 가지.**

1. **무엇을 기억하는가** — 커서인가 집합인가.
2. **언제 갱신하는가** — 처리 전인가 후인가. (전이면 실패한 항목이 사라지고, 후면 중복 처리 위험이 있다)
3. **실패하면 되돌리는가** — 4단계 스크립트는 `claude -p` 가 실패해도 커서를 올린다. 그러면 그 편지는 영원히 안 읽힌다.

세 질문에 답을 정하지 않은 루프는 **조용히 일을 흘린다.** 실패해도 로그에 안 남기 때문에 몇 주 뒤에야 알게 된다. 이걸 고치는 것이 실습 과제 1번이다.

| 첫 틱부터 "할 일 없음" | 커서가 이미 끝에 있다 | `echo 0 > loop/cursor.txt` |
| `sed: -e expression` 오류 | 커서가 숫자가 아니다 | `cat loop/cursor.txt` 확인 |

**3단계의 `/context` 화면이 이 실습의 전부다.** 항목별로 무엇이 얼마나 들어 있는지 나온다. 대략 이런 모양이다.

- `Memory` — `S2-2`에서 만든 `CLAUDE.md`
- `Messages` — 내가 실제로 친 말

**내가 친 말은 맨 아래 한 줄이고, 그 위가 전부 준비물이다.**

이게 에이전트 비용의 실제 모양이다. **비용은 내가 무엇을 물었느냐가 아니라 에이전트가 무엇을 들고 다니느냐로 결정된다.** 그래서 비용을 줄이는 가장 큰 레버는 프롬프트를 짧게 쓰는 것이 아니라 —

2. **작은 모델을 쓰는 것** (`S1-4`에서 품질 차이가 거의 없음을 확인했다)
3. **도구 목록을 줄이는 것** (준비물 자체를 줄인다)

### 예산을 넘겨서 나간 것은 버그가 아니다

8단계에서 예산은 0.002 달러인데 실제로는 그보다 많이 나갔을 것이다.

이유는 이렇다. **예산은 턴 사이에 검사된다.** 진행 중인 턴을 중간에 잘라내지 않는다. 한 턴이 예산을 넘기면 그 턴이 끝난 뒤에 중단된다.

그래서 `--max-budget-usd` 는 **정확한 천장이 아니라 폭주를 멈추는 브레이크**다. `S2-4`의 게이트에 상한을 안 걸었을 때처럼 무한히 도는 상황을 멈추는 용도다. 실무에서는 한 턴의 예상 비용보다 충분히 큰 값을 걸고, 정확한 통제는 프롬프트 범위와 도구 범위로 한다.

**그리고 오류로 끝난다는 것을 기억해 둔다.** 자동화에서 예산에 걸리면 그 잡은 실패로 처리된다. 재시도 로직이 그대로 다시 돌면 또 예산까지 쓰고 실패한다.

### 이 기록에 무엇이 남는지 알고 있어야 한다

5단계에서 센 폴더에는 **주고받은 내용이 그대로** 남는다. 파일 내용, 명령, 답변 전부다. `S2-1`에서 만든 `secrets/keys.env` 를 실수로 읽었다면 그 값도 여기 남는다. (`S2-1` 10단계에서 그게 없다는 것을 확인했다.)

**이건 관측의 재료이면서 동시에 유출 경로다.** 회사 코드로 이 실습을 하고 있다면 이 폴더의 위치와 보존 기간을 알고 있어야 한다.

### 창 안에서는 `#` 한 줄이면 된다

2단계를 프롬프트로 시켰지만, 창에서는 더 쉬운 방법이 있다. **줄 맨 앞에 `#` 을 붙여서 치면 그 내용이 바로 `CLAUDE.md` 에 추가된다.**

```prompt
# 배포는 매주 화요일이다
```

`/memory` 로 확인하면 늘어나 있다. **기억을 남기는 데 문장 하나면 된다는 것이 요점이다.** 그래서 오히려 위험하다 — 아무나 아무거나 적을 수 있고, 그게 그 폴더의 모든 세션에 영향을 준다.

### 대화 이어받기를 자동화에서 쓰면 안 되는 이유

9단계의 이어받기는 편리하지만 **대상이 암묵적이다.** "이 폴더의 마지막 세션"을 이어받는데, 그 마지막이 무엇인지는 언제 누가 무엇을 돌렸느냐에 달렸다.

- 다른 터미널에서 창을 하나 더 띄우면 대상이 바뀐다.
- 세션이 길어지면 문맥이 압축되면서 초반 내용이 사라진다.
- 루프에서 도는 잡이 사람의 세션을 이어받을 수도 있다.

**자동화에서는 애초에 파일에 적는다.** `S3-3`의 `cursor.txt` 가 그것이다. 그리고 파일에 적으면 `git log` 로 "누가 언제 이 사실을 추가했는지"가 남는다. 세션 기록에는 그게 없다.

### 2단계에서 "기존 내용은 지우지 마라"를 넣은 이유

5단계에서 규칙 마커를 센 것이 그 확인이다. 파일에 추가하라고 시키면 에이전트가 **통째로 다시 쓰는** 일이 흔하다. 그러면 `S2-2`에서 심은 규칙 네 개가 조용히 사라진다.

**에이전트에게 기억 파일을 맡길 때는 반드시 "덧붙여라, 지우지 마라"를 명시하고, 그다음에 확인한다.** 그리고 그 파일은 git 으로 추적해야 한다.

## S4-2. 에이전트의 발자국을 그래프로 연다

> 짝 | [C4-2](#lab-c4-2)
> 단계 | 8
> 모델 | haiku 1회 (분석을 시킨다)
> 끝나면 | 도구별 호출 횟수와, 어디서 헤맸는지

### 이 실습의 한 문장

지금까지 이 폴더에서 에이전트가 부른 도구를 전부 세고, **어떤 도구 다음에 어떤 도구가 왔는지**까지 뽑는다.

### 왜 이게 그래프인가

노드는 도구, 간선은 "A 다음에 B가 왔다"이다. 그게 전부다. **그래프는 특별한 자료구조가 아니라 관계를 세는 방식이다.**

이걸 보면 세 가지가 드러난다. 어떤 도구를 실제로 쓰는가(설계와 다를 수 있다), 어디서 헤매는가(같은 도구 반복), 어떤 순서가 굳어졌는가.

### 단계

**1 · 창을 열어 지난 대화 목록을 본다**

```bash
cd ~/cc-step && claude --model haiku
```

```prompt
/resume
```

```screen
   Resume session (1 of 18)
   ╭────────────────────────────────────────────────────────────────────────╮
   │ ⌕ Search…                                                              │
   ╰────────────────────────────────────────────────────────────────────────╯
     cc-step

   ❯ f23c8cb7
     2 minutes ago · master · 6.2KB

     Ctrl+A to show all projects · Ctrl+B to only show current branch · Space
     to preview · Ctrl+R to rename · Type to search · Esc to cancel
```

`Esc` 로 목록을 닫는다. **이 목록이 원자료다.** 하지만 눈으로 세기에는 너무 많다.

**2 · 분석을 클로드코드에게 시킨다**

```prompt write
~/.claude/projects 아래에서 이 폴더(cc-step)에 해당하는 기록 폴더를 찾아라. 그 안의 모든 .jsonl 파일에서 도구 호출(tool_use)을 세어서, 도구 이름별 호출 횟수를 많은 순으로 표로 보여줘. 그리고 같은 도구가 연달아 두 번 불린 경우가 몇 번인지도 세어라. 결과를 work/journey.md 에 저장해라.
```

```prompt
/exit
```

**3 · 결과를 본다**

```bash
cat work/journey.md
```

`work/` 아래에 저장하라고 시킨 것에 주의한다. `S2-2`에서 심은 폴더 규칙 때문이다. **그냥 `journey.md` 라고 시키면 에이전트가 알아서 `work/` 안에 만든다** — 그러면 이 `cat` 이 파일을 못 찾는다. 규칙을 심었으면 그다음부터는 규칙에 맞춰 말해야 한다.

**4 · 같은 것을 셸로 직접 세어 본다** — 답이 맞는지 대조한다

```bash
cd ~/cc-step && DIR=~/.claude/projects/"$(pwd | tr '/' '-')" && cat "$DIR"/*.jsonl | grep -o '"name":"[A-Za-z_0-9]*","input"' | cut -d'"' -f4 > tools.txt && wc -l tools.txt
```

**5 · 도구별 횟수를 센다** — 이게 노드다

```bash
sort tools.txt | uniq -c | sort -rn
```

**6 · 막대로 그린다**

```bash
sort tools.txt | uniq -c | sort -rn | awk '{printf "  %-26s %4d  ", $2, $1; for (i = 0; i < $1 && i < 40; i++) printf "#"; print ""}'
```

**7 · 전이를 뽑는다** — 이게 간선이다

```bash
paste tools.txt <(tail -n +2 tools.txt) | sort | uniq -c | sort -rn | head -12
```

`tail -n +2` 는 "둘째 줄부터"다. 원본과 한 칸 밀린 것을 나란히 붙이면 **연속한 두 도구 쌍**이 된다.

**8 · 같은 도구가 연달아 나온 곳만 본다** — 헤매는 신호다

```bash
paste tools.txt <(tail -n +2 tools.txt) | awk '$1 == $2' | sort | uniq -c | sort -rn
```

### 기대 결과

**세 가지를 읽어 낸다.**

**첫째, 도구 분포가 설계와 다르다.** `Bash` 와 `Read` 가 압도적으로 많고 내가 공들여 만든 커넥터는 몇 번뿐이다. 나는 스킬과 커넥터를 만들었는데 에이전트는 대부분 기본 도구를 썼다. **도구를 만들었다고 쓰이는 게 아니다.**

`ToolSearch` 나 `WebFetch` 가 한두 번 있다면 그건 `S2-1`에서 `curl` 이 막혔을 때 우회 경로를 찾던 흔적이다. **그래프에는 막힌 순간이 남는다.**

**둘째, 8단계의 자기 자신 전이가 헤맨 자리다.** `Bash → Bash`, `Read → Read`. 한 번에 원하는 것을 못 찾아 다시 부른 것이다. 이 쌍이 많은 도구가 **개선 우선순위**다. 도구의 출력이 부족했거나 설명이 모호했다는 뜻이기 때문이다.

`Skill → Skill` 도 보인다. `S1-2`에서 두 스킬이 연달아 발동한 것이 여기 남았다.

**셋째, 굳어진 순서가 보인다.** `Bash → Read` 같은 쌍이 자주 나오면 그건 도구 두 개가 아니라 **하나여야 한다는 신호**일 수 있다. 왕복이 줄면 문맥과 비용이 함께 준다.

### 2단계와 4단계를 나란히 놓고 보라

**같은 일을 두 번 했다.** 한 번은 클로드코드에게 시켰고(2단계), 한 번은 셸로 직접 셌다(4~8단계).

**둘 다 필요하다.** 이유가 다르다.

| | 클로드코드에게 시키기 | 셸로 직접 세기 |
|---|---|---|
| 빠르다 | 한 문장 | 명령 다섯 개 |
| 형식 | 매번 다르다 | 항상 같다 |
| 재현 | 안 된다 | 된다 |
| 비용 | 모델 호출 | 0 |
| 틀렸을 때 | 알기 어렵다 | 명령을 보면 안다 |

**한 번 볼 것은 시켜서 보고, 계속 볼 것은 셸로 만든다.** 그리고 시켜서 본 답이 맞는지는 **한 번쯤 손으로 대조해야 한다** — 4단계가 그것이다. 이 트랙에서 판정을 늘 셸에 맡긴 이유이기도 하다.

### 이 분석에 모델을 부른 것은 한 번뿐이다

4~8단계는 모델을 한 번도 안 부른다. 기록은 이미 디스크에 있었다. **관측은 대체로 공짜다.**

그리고 여기서부터의 명령은 앞의 실습들보다 조금 거칠다. `grep -o` 로 JSON 을 긁고 `paste` 로 줄을 밀어 붙인다. **그게 이 실습의 성격이다** — 화면으로 볼 수 없는 것을 보는 일이고, 그럴 때는 로그 분석 도구를 쓴다. 앞의 실습들이 화면과 파일로 끝났던 것과 대비해 두면 좋다.

## S4-3. 근거 없는 주장을 잡아내는 대조기를 만든다

> 짝 | [C4-3](#lab-c4-3)
> 단계 | 10
> 모델 | haiku 1회
> 끝나면 | 인용을 원문과 문자 그대로 대조하는 `check.sh`

### 이 실습의 한 문장

에이전트에게 **주장마다 원문 문장을 그대로 복사해서 붙이게** 하고, 그 인용이 원문에 진짜 있는지 `grep` 으로 대조한다.

### 단계

**1 · 노트를 하나 더 만든다**

```bash
cd ~/cc-step && printf '# 8월 15일 팀 회의\n참석: 김, 이\n결정: 배포 자동화 도구는 도입하지 않는다. 당장은 수동 절차를 문서화한다.\n보류: 스테이징 환경 분리는 다음 분기에 다시 논의한다.\n' > notes/2026-08-15-회의.md
```

**2 · 원문을 한 파일로 합친다**

```bash
cat notes/*.md > source.md && wc -l source.md
```

**3 · 스키마를 변수에 담는다** — 출력의 모양을 못 박는다

```bash
SCHEMA='{"type":"object","properties":{"claims":{"type":"array","items":{"type":"object","properties":{"claim":{"type":"string","description":"주장 한 문장"},"quote":{"type":"string","description":"source.md 에서 그대로 복사한 근거 문장"}},"required":["claim","quote"]}}},"required":["claims"]}'
```

**4 · 정리를 시킨다** — 인용을 그대로 복사하라고 강조한다

```bash
claude -p "source.md 를 읽고, 지금까지 팀이 내린 결정과 보류 사항을 정리해라. 각 항목마다 반드시 source.md 안의 문장을 한 글자도 바꾸지 않고 그대로 복사해서 quote 에 넣어라. 요약하거나 다듬지 마라." --model haiku --json-schema "$SCHEMA" > claims.json 2>/dev/null
```

**5 · 결과를 본다**

```bash
cat claims.json
```

**6 · 주장과 인용을 두 파일로 뽑는다**

```bash
grep -o '"claim":[[:space:]]*"[^"]*"' claims.json | cut -d'"' -f4 > claims.txt
```

```bash
grep -o '"quote":[[:space:]]*"[^"]*"' claims.json | cut -d'"' -f4 > quotes.txt
```

**7 · 짝을 맞춘다**

```bash
paste -d'|' claims.txt quotes.txt > pairs.txt && cat pairs.txt
```

**8 · 대조기를 만든다** — 셸 12줄. LLM 을 쓰지 않는다

```bash
cat > check.sh <<'EOF'
#!/usr/bin/env bash
# 주장마다 딸린 인용이 원문에 문자 그대로 있는지 대조한다.
BAD=0; N=0
while IFS='|' read -r CLAIM QUOTE; do
  N=$((N + 1))
  if [ -z "$QUOTE" ]; then
    echo "FAIL  근거 없음        · $CLAIM"; BAD=$((BAD + 1))
  elif grep -qF "$QUOTE" source.md; then
    echo "PASS  $CLAIM"
    echo "      근거: $QUOTE"
  else
    echo "FAIL  원문에 없는 인용 · $CLAIM"
    echo "      인용: $QUOTE"; BAD=$((BAD + 1))
  fi
done < "$1"
echo "── $((N - BAD))/$N 통과 · $BAD개 실패"
[ "$BAD" -eq 0 ]
EOF
chmod +x check.sh
```

**9 · 돌린다**

```bash
./check.sh pairs.txt; echo "→ exit $?"
```

**10 · 거짓 주장 두 개를 끼워 넣고 다시 돌린다**

```bash
cp pairs.txt pairs-bad.txt
```

```bash
echo "배포 자동화 도구를 다음 주에 도입한다.|결정: 배포 자동화 도구를 다음 주에 도입한다." >> pairs-bad.txt
```

```bash
echo "예산이 30% 증액되었다.|" >> pairs-bad.txt
```

```bash
./check.sh pairs-bad.txt; echo "→ exit $?"
```

### 기대 결과


**주장(왼쪽)과 인용(오른쪽)이 다른 문장인 것을 보라.** 주장은 모델이 요약한 것이고 인용은 원문에서 복사한 것이다. **요약은 자유롭게 하되 근거는 손대지 못하게** 한 것이 이 설계의 요점이다.

**10단계에서 넣은 첫 번째 거짓말을 보라.** 원문은 "도입하지 않는다"이고 가짜 인용은 "도입한다"이다. **단어 하나가 빠져서 정반대가 됐다.**

이게 환각의 흔한 형태다. 완전히 없는 이야기를 지어내는 것보다, 있는 문장을 미세하게 비트는 쪽이 훨씬 잦고 훨씬 위험하다. 사람 눈으로는 잘 안 걸린다.

### 왜 "의미상 같으면 통과"로 하면 안 되는가

`grep -qF` 는 **문자 그대로** 찾는다(`-F` 는 정규식 해석 없이 고정 문자열). 유연하지 않다. 인용에 마침표 하나만 달라도 실패한다.

그게 **의도한 것이다.** 이유가 둘이다.

**첫째, 의미 판정에는 다시 LLM 이 필요하다.** 그러면 판정자가 판정 대상만큼 복잡해지고, 판정자의 오류는 누가 검증하나. 검증기는 검증 대상보다 단순해야 한다.

**둘째, 미세 변형을 잡는 것이 목적이다.** 의미 판정기는 "도입한다"와 "도입하지 않는다"를 비슷하다고 볼 수 있다. 문자열 대조는 **반드시** 잡는다.

인용이 너무 엄격해서 자꾸 실패한다면, 고칠 곳은 검증기가 아니라 **프롬프트**다. 4단계의 "한 글자도 바꾸지 말고 그대로 복사해라"가 그 장치다.

### 여기서만 창을 안 여는 이유 — 구조화 출력은 자동화 전용이다

4단계는 이 실습에서 유일하게 `-p` 를 쓴다. `--json-schema` 때문이다.

**대화창에는 이 기능이 없다.** 창은 사람이 읽을 답을 내놓는 자리이고, 스키마는 기계가 읽을 답을 강제하는 장치다. 창에서 같은 일을 하려면 "아래 형식으로만 답해라"를 프롬프트에 넣어야 하는데, **그러면 형식이 흔들린다.**

이건 `S3-*`의 루프와 같은 구분이다. **사람이 읽을 것은 창에서, 기계가 읽을 것은 `-p` 로.** 그리고 검증기가 뒤에 붙는 순간 그건 기계가 읽을 것이다.

### 스키마를 쓴 이유

3단계의 `--json-schema` 가 없으면 모델은 매번 다른 모양으로 답한다. 표로 줬다가 목록으로 줬다가 한다. 그러면 6단계의 `grep` 이 안 걸린다.

**출력의 모양을 못 박는 것이 검증의 전제 조건이다.** 형식이 흔들리면 그 뒤의 모든 자동 판정이 무너진다.

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| `claims.json` 이 JSON 이 아니다 | 스키마가 안 먹었다 | `cat claims.json` 으로 확인, 3단계 따옴표 확인 |
| 6단계 결과가 비었다 | 필드 이름이 다르다 | `cat claims.json` 에서 실제 키를 본다 |
| 전부 FAIL | 모델이 요약해서 인용했다 | 4단계 프롬프트의 "그대로 복사" 를 강조해 다시 |
| 9단계에서 항목이 3개 이하 | 노트가 적다 | 정상이다 |
| 인용에 `\|` 가 들어갔다 | 7단계 구분자와 충돌 | 노트에 세로줄 문자를 안 쓰면 된다 |

### 클로드코드 안에서 하려면

창 안에서는 `--json-schema` 를 쓸 수 없다. 대신 "아래 형식으로만 답해라"를 프롬프트에 넣고 같은 일을 할 수 있지만, 형식이 흔들린다. **자동 검증이 필요하면 `-p` 모드와 스키마를 쓴다.** 이게 두 모드의 실질적인 차이 중 하나다.

## S5-1. 명세 없이 시킨 것과 명세로 시킨 것을 나란히 놓는다

같은 기능을 두 번 만들게 한다 — 한 번은 한 줄 요청으로, 한 번은 명세로. 그리고 **둘 다 모르는 시험**으로 채점한다.

### 단계

**1 · 폴더를 만든다**

**2 · 숨겨진 시험 항목을 적는다** — 두 라운드 모두 이걸 못 본다

**3 · 채점기를 만든다** — 셸 20줄

```bash
cat > work/sdd/hidden/accept.sh <<'EOF'
#!/usr/bin/env bash
# 숨겨진 수용 시험. 인자는 검사할 스크립트 경로.
T="$1"
D="$(cd "$(dirname "$0")" && pwd)"
[ -f "$T" ] || { echo "$T 가 없다"; exit 1; }
BAD=0; N=0
while IFS='|' read -r IN WANT; do
  N=$((N + 1))
  GOT=$(bash "$T" "$IN" 2>/dev/null)
  if [ "$GOT" != "$WANT" ]; then
    echo "FAIL  [$IN] -> [$GOT]  (기대 [$WANT])"; BAD=$((BAD + 1))
  fi
done < "$D/cases-ok.txt"
while IFS= read -r IN; do
  N=$((N + 1))
  if bash "$T" "$IN" > /dev/null 2>&1; then
    echo "FAIL  [$IN] 는 오류여야 한다 (종료 코드 0 이 나왔다)"; BAD=$((BAD + 1))
  fi
done < "$D/cases-err.txt"
N=$((N + 1))
if bash "$T" "" > /dev/null 2>&1; then
  echo "FAIL  빈 문자열은 오류여야 한다"; BAD=$((BAD + 1))
fi
echo "$((N - BAD))/$N 통과"
[ "$BAD" -eq 0 ]
EOF
chmod +x work/sdd/hidden/accept.sh
```

```bash

# 명세: duration.sh

## 목표

사람이 쓰는 기간 표기 문자열을 초 단위 정수로 바꾼다.

## 사용자 시나리오

설정 파일에 `timeout: 1h30m` 처럼 적으면, 스크립트가 `5400` 을 출력해야 한다.

## 기능 요구사항

- `duration.sh <문자열>` 형태로 인자 하나를 받는다.
- 정상이면 초 단위 정수 하나만 표준 출력에 한 줄로 쓰고 종료 코드 0 으로 끝낸다.
- 오류면 표준 출력에 아무것도 쓰지 않고 종료 코드 1 로 끝낸다.
- 단위는 `h`(시), `m`(분), `s`(초) 세 개만 인정한다.
- 여러 단위를 이어 쓸 수 있다. 예: `2h15m30s` → 8130.
- 단위 순서는 반드시 큰 것에서 작은 것으로만 온다.
- 대문자 단위도 같게 처리한다. `1H30M` → 5400.

## 경계 사례와 규칙

- 같은 단위가 두 번 나오면 오류다. `1h2h`.
- 순서가 큰 것에서 작은 것이 아니면 오류다. `30m1h`.
- 숫자 없는 단위는 오류다. `m30`.
- 단위 없는 숫자는 오류다. `90`.
- 빈 문자열은 오류다.
- 알 수 없는 문자가 있으면 오류다. `1x`, `abc`.
- 음수는 오류다. `-5m`.
- 소수는 오류다. `1.5h`.
- 단위 값에 상한을 두지 않는다. `90m` 은 5400 으로 정상 처리한다.
- `0s` 는 0 을 출력한다. 오류가 아니다.

## 수용 기준

- 위 `기능 요구사항` 의 예시 전부가 정확한 정수를 출력한다.
- 위 `경계 사례와 규칙` 의 모든 오류 입력이 종료 코드 1 로 끝난다.
- 오류일 때 표준 출력에 숫자가 섞여 나오면 실패로 본다.

## 범위 밖

- 일(`d`)·주(`w`)·밀리초(`ms`) 단위는 이번 범위가 아니다.
- 역변환(초 → 문자열)은 만들지 않는다.
- 공백을 허용하는 표기(`1h 30m`)는 이번 범위가 아니다.
EOF
```

**두 라운드의 차이는 모델이 아니다.** 같은 모델, 몇 분 차이다. 다른 것은 **내가 무엇을 말했는가**뿐이다.

**라운드 A의 코드 일곱 줄을 읽어 보라.** 나쁜 코드가 아니다. `1h30m` 을 5400으로 바꾸라고 했고 정확히 그걸 한다. 문제는 **그것만** 한다는 것이다. `abc` 를 주면 0을 출력하고 종료 코드 0으로 끝난다. 잘못된 입력이라는 개념 자체가 없다.

**라운드 A가 놓친 아홉 개는 모델이 게을러서가 아니다. 내가 안 물었기 때문이다.** "1h30m 을 초로 바꿔라"라는 문장에는 "abc 를 주면 어떻게 되나"에 대한 답이 없다. 사람이 그 문장을 받아도 똑같이 물어봐야 한다.

**두 번 돌려도 점수가 같다.** 이 문서를 만들며 두 번 실행했는데 라운드 A는 두 번 다 7/16, 라운드 B는 두 번 다 16/16 이었다. 코드 줄 수는 7줄과 16줄로 달랐지만 **점수는 같았다.** 명세가 있고 없고의 차이는 우연이 아니다.

**그리고 코드 길이를 보라.** 명세 32줄로 코드 69~72줄을 얻었다. "명세 쓸 시간에 코드를 쓰겠다"는 반론이 나오는 지점이다. 답은 이렇다 — 라운드 A의 7줄은 **틀린 7줄**이고, 그게 틀렸다는 것을 알려면 결국 16개의 시험 항목이 필요하다. 그 시험 항목이 바로 명세다. **명세를 안 쓰면 명세가 없어지는 게 아니라, 명세가 사람 머릿속에 남고 검증할 수 없게 된다.**

### 계획 모드가 왜 따로 있는가

10단계는 파일을 만들지 않는다. 무엇을 만들지만 말한다. 나오는 것은 이런 모양이다.

```
(이 세션에서는 ExitPlanMode 도구가 비활성화되어 있어 호출할 수 없으므로,
 계획 승인 여부는 텍스트로 확인 부탁드립니다.)

- 파일: work/duration.sh (신규, 실행권한 부여)
- 지원 단위: d(86400), h(3600), m(60), s(1), 연결 표기 지원 (예: 1d2h30m10s)
- 정수만 지원, 단위 없는 순수 숫자는 오류 처리
- bash [[ =~ ]] 정규식으로 앞에서부터 숫자+단위 토큰을 반복 파싱해 합산
- 빈 입력/잘못된 형식은 stderr 안내 + 종료코드 1
- 검증: 1h30m→5400, 2d→172800, 빈 문자열/abc 오류 케이스 실행 확인

이 방향으로 진행해도 될지, 아니면 변경이 필요하면 알려주세요.
```

마지막 줄이 계획 모드의 요점이다. **에이전트가 멈춰서 물어본다.**

**읽을 것이 셋 더 있다.**

1. **`d`(일) 단위가 계획에 들어 있다.** `S5-1`의 명세는 일 단위를 `범위 밖`으로 못 박았는데, 여기서는 명세를 안 줬으니 모델이 "있으면 좋겠지"라고 넣었다. **`S5-4`에서 잡게 될 표류가 계획 단계에서 이미 태어난다.**
2. **파일 위치가 `work/duration.sh` 다.** `S2-2`에서 심은 폴더 규칙이 계획에까지 영향을 준다.
3. **첫 줄의 안내 문구.** `-p` 모드에는 승인해 줄 사람이 없어서 `ExitPlanMode` 도구가 꺼져 있다. 그래서 에이전트가 계획만 말하고 멈췄다. **대화창에서는 여기서 승인/거절 버튼이 뜬다.**

이게 명세 주도 개발의 축소판이다. **에이전트가 코드를 쓰기 전에 사람이 개입할 자리를 만드는 것.** 계획을 읽고 "그건 아니다"라고 말할 수 있다면, 잘못된 방향으로 200줄을 짜고 나서 되돌리는 것보다 훨씬 싸다.

계획 모드는 명세보다 가볍고 대화보다 무겁다. 순서는 이렇다 — 애매하면 `S5-2`의 인터뷰로 질문을 뽑고, 답을 모아 명세를 쓰고, 명세로 계획을 세우고, 계획으로 만든다.

### 계획 모드는 먼저 둘러본다 — 빈 폴더에서는 그게 함정이 된다

10단계 프롬프트에 "다른 파일을 찾거나 읽지 마라"를 넣은 이유가 있다.

처음에는 그 문장 없이 돌렸다. **에이전트가 서브에이전트를 띄워 상위 폴더를 뒤지기 시작했고, 샌드박스에 막히고, 다시 시도하고, 몇 분이 지나도 계획이 안 나왔다.** 계획을 세우기 전에 "지금 코드가 어떻게 생겼는지" 먼저 보려 한 것인데, `roundP` 는 방금 만든 빈 폴더였다.

**이건 계획 모드의 버그가 아니라 성질이다.** 실제 저장소에서는 둘러보는 것이 옳다 — 기존 코드를 모르고 세운 계획은 쓸모가 없다. 하지만 빈 폴더에서는 둘러볼 것이 없고, 모델은 그 사실을 미리 알지 못한다.

여기서 얻을 것 둘.

1. **탐색을 시킬지 말지는 내가 정해서 말해 줘야 한다.** "이 폴더는 비어 있다"는 한 줄이 몇 분을 아낀다.
2. **자동화에서 계획 모드를 쓸 때는 반드시 상한을 건다.** `--max-budget-usd 0.2` 를 붙인 것이 그것이다. 탐색은 끝을 스스로 정하지 않는다 — `S3-4`에서 본 것과 같은 이유다.

### `--allowedTools` 를 붙인 이유 — 승인해 줄 사람이 없다

5단계와 8단계에 `--allowedTools "Read" "Write" "Edit" "Bash"` 가 붙어 있다.

이게 없으면 이런 일이 생긴다. `build.txt` 에 답 대신 이 한 줄만 들어 있다.

```
파일 작성 권한이 필요합니다. 승인해 주세요.
```

**`--permission-mode acceptEdits` 를 줬는데도 그렇다.** 이 트랙을 세 번 돌리면서 두 번은 되고 한 번은 안 됐다. 상위 `~/cc-step` 의 권한 규칙(`S2-1`·`S2-3`에서 만든 것)이 어떻게 합쳐지는지, 그리고 모델이 승인을 물을지 그냥 쓸지가 매번 같지 않다.

`--allowedTools` 는 **그 실행에서 쓸 수 있는 도구를 명령줄에서 못 박는다.** 설정 파일보다 우선이고 확실하다. 대신 **여기 없는 도구는 못 쓴다** — `S1-3`에서 커넥터 두 개만 준 것과 같은 장치다.

**자동화에서는 이 방식이 기본이다.** 설정 파일에 기대면 "그 폴더에 뭐가 있느냐"에 결과가 달라진다. 명령줄에 적으면 그 명령만 보고 무엇을 할 수 있는지 알 수 있다.

### 5단계 — 규칙이 부딪히면 아래에서 덮는다

`S2-2`에서 심은 규칙 2번은 **"파일은 `work/` 아래에만 만든다"** 였다. 여기는 이미 `work/sdd/roundA` 안인데, 그 규칙을 곧이곧대로 적용한 에이전트가 `roundA/work/duration.sh` 를 만들어 버린다. 그러면 7단계의 채점기가 파일을 못 찾는다.

**이 문서를 만들면서 실제로 겪었다.** 프롬프트에 "지금 이 폴더의 duration.sh 다", "하위 폴더를 만들지 마라"를 넣어도 규칙이 이겼다.

**해결은 프롬프트를 더 세게 쓰는 것이 아니라 규칙을 고치는 것이다.** `CLAUDE.md` 는 상위 폴더에서 하위 폴더로 상속되고, **하위 폴더의 `CLAUDE.md` 가 더 가깝다.** 그래서 `work/sdd/CLAUDE.md` 하나로 그 아래 전부에서 예외가 선다.

여기서 얻을 것 셋.

1. **규칙은 계층이다.** 전역 → 프로젝트 → 하위 폴더 순으로 가까운 것이 이긴다.
2. **예외는 프롬프트가 아니라 규칙 층에서 낸다.** 프롬프트로 매번 우회하면 그 우회를 기억해야 할 사람이 늘어난다.
3. **예외에는 이유를 적는다.** 5단계 파일의 둘째 문단이 그것이다. 이유 없는 예외는 몇 달 뒤에 지워진다.

**예외를 쓸 때도 애매하면 안 된다.** 처음에는 "지금 있는 폴더에 그대로 만든다"라고만 썼는데, 에이전트가 그것을 **규칙 파일이 있는 폴더**(`work/sdd`)로 읽고 거기에 만들었다. `pwd` 라고 못 박고 나서야 의도대로 돌았다. **규칙을 고칠 때도 "사람마다 다르게 읽을 지점"이 생긴다** — `S5-2`가 그걸 찾는 실습이다.

이 트랙에서 그 규칙 하나가 **일곱 번** 사고를 냈다. `S3-3`, `S4-2`, `S5-1`(계획 모드), `S5-1`(라운드 A 두 번), `S5-2`, `S5-3`. **규칙은 심는 순간이 아니라 몇 주 뒤 다른 작업에서 비용을 청구한다.**

### `work/sdd/` 아래에서 하는 이유

`S2-2`에서 심은 규칙 2번(`work/` 아래에만 만든다) 때문이다. `~/cc-step/sdd/` 에서 시켰다면 에이전트가 `sdd/work/duration.sh` 를 만들어서 채점기가 파일을 못 찾는다.

**이 문서를 만들면서 실제로 겪은 일이다.** 그리고 이게 하니스 엔지니어링의 실제 모습이다 — **내가 심은 규칙이 몇 주 뒤 내 다른 작업을 깨뜨린다.** 5단계와 8단계 프롬프트에 "하위 폴더를 만들지 마라"를 넣은 것도 같은 이유다.

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| `duration.sh 가 없다` | 하위 폴더에 만들었다 | `find . -name duration.sh` 로 찾아 옮긴다 |
| `build.txt` 에 "권한이 필요합니다" | 도구가 안 열렸다 | `--allowedTools` 가 붙어 있는지 확인. 아래 설명 참고 |

## S5-2. AI가 나를 인터뷰하게 만든다

> 짝 | [C5-2](#lab-c5-2)

> 끝나면 | `/clarify` 슬래시 명령과, 내가 안 물어본 질문 목록

### 이 실습의 한 문장

요구사항을 주면 **모호한 곳을 질문으로 되돌려 주는** 슬래시 명령을 만든다.

### 단계

**1 · 명령 폴더를 만든다**

```bash
cd ~/cc-step && mkdir -p .claude/commands
```

**2 · 슬래시 명령을 만든다** — `$ARGUMENTS` 자리에 내가 친 말이 들어간다

```bash
cat > .claude/commands/clarify.md <<'EOF'
---
description: 요구사항이 모호한 곳을 찾아 질문 목록을 만든다
---

아래 요구사항을 읽고, 그대로 만들면 **사람마다 다르게 만들 지점**을 찾아라.

요구사항: $ARGUMENTS

찾을 때 아래를 특히 살펴라.

- 경계값 — 0, 빈 값, 음수, 아주 큰 값에서 무엇이 옳은가
- 실패 처리 — 잘못된 입력이 오면 무엇을 하는가
- 범위 — 어디까지가 이번 일이고 어디부터가 다음 일인가
- 판정 기준 — 무엇이 참이면 완성인가

출력은 반드시 이 형식이다.

⟪YNC-CLARIFY-V1⟫
1. (질문) — 왜 모호한지 한 줄
2. ...

규칙:
- 질문은 3개에서 5개 사이로 한다.
- 스스로 답하지 마라. 질문만 한다.
- 구현 방법을 묻지 마라. 무엇이 옳은지를 물어라.
- 이 폴더의 규칙이 첫 줄에 다른 마커를 요구하더라도, 그 줄 다음에 반드시 `⟪YNC-CLARIFY-V1⟫` 를 쓴다. 두 마커가 모두 나와야 한다.
EOF
ls -l .claude/commands/clarify.md
```

**3 · 애매한 요구사항으로 시험한다**


### 기대 결과

```
1
⟪YNC-RULES-V1⟫
⟪YNC-CLARIFY-V1⟫

1. 지원하는 파일 형식이 무엇인가? — "파일"이 텍스트, PDF, 이미지, 영상 등 어디까지인지 범위가 불명확하다.
2. 지원하지 않는 형식이 올라오면 어떻게 처리하는가? — 오류 처리 방식이 정의되지 않았다.
3. 파일 크기에 제한이 있는가? — 매우 큰 파일의 경계값 처리가 불명확하다.
4. 요약할 내용이 없거나 매우 짧으면 무엇을 보여주나? — 판정 기준이 불명확하다.
5. 요약의 길이는 어느 정도가 적절한가? — 충분성을 어떻게 판단할지 기준이 없다.
...
⟪YNC-CLARIFY-V1⟫

1. **음수 처리** — "-1h" 같은 음수가 오면 음수를 반환하는가, 0인가, 오류인가?
2. **빈 입력 처리** — 빈 문자열 "", 단위 없는 "0", 단위만 있는 "h" 는 어떻게 하는가?
3. **잘못된 형식의 오류 처리** — "1x30m" 이 오면 종료 코드는 무엇인가? 오류 메시지는 stderr 인가?
4. **대소문자 처리** — "1H30M" 처럼 대문자가 섞이면 인식하는가?
5. **단위 순서 제약** — "30m1h" 처럼 순서가 뒤바뀌면 허용하는가, 오류인가?
...
## 경계 사례와 규칙

- 같은 단위가 두 번 나오면 오류다. `1h2h`.
- 순서가 큰 것에서 작은 것이 아니면 오류다. `30m1h`.
- 숫자 없는 단위는 오류다. `m30`.
- 단위 없는 숫자는 오류다. `90`.
- 빈 문자열은 오류다.
- 알 수 없는 문자가 있으면 오류다. `1x`, `abc`.
- 음수는 오류다. `-5m`.
- 소수는 오류다. `1.5h`.
```

**4단계와 5단계를 나란히 놓고 보라.**

| AI 가 물은 것 | 명세의 어느 줄인가 |
|---|---|
| 음수 처리 | 음수는 오류다. `-5m` |
| 빈 입력 처리 | 빈 문자열은 오류다 |
| 잘못된 형식의 오류 처리 | 알 수 없는 문자가 있으면 오류다. `1x`, `abc` |
| 대소문자 처리 | 대문자 단위도 같게 처리한다. `1H30M` |
| 단위 순서 제약 | 순서가 큰 것에서 작은 것이 아니면 오류다. `30m1h` |

**다섯 개가 다 있다.** 그 명세는 내가 앉아서 고민해서 쓴 것이다. 그런데 그 고민의 대부분은 **기계가 몇 초 만에 뽑아낼 수 있는 종류**였다. 경계값, 실패 처리, 범위, 판정 기준 — 이 넷은 거의 모든 요구사항에서 빠지는 자리다.

**AI 는 답을 모른다. 하지만 무엇을 안 물었는지는 안다.** 그러니 명세를 혼자 쓰지 마라. 초안을 던지고 질문을 받아라.

### 마커가 두 개 나온다 — 그리고 처음엔 하나도 안 나왔다

기대 결과의 첫 두 줄이 `⟪YNC-RULES-V1⟫` 와 `⟪YNC-CLARIFY-V1⟫` 다. 앞의 것은 `S2-2`에서 `CLAUDE.md` 에 심은 폴더 규칙이 요구한 것이고, 뒤의 것은 이 슬래시 명령이 요구한 것이다.

**이 문서를 만들 때 처음에는 클래리파이 마커가 아예 안 나왔다.** 명령 파일에는 "출력은 반드시 이 형식이다"라고 써 두었는데도 그랬다.

원인은 이렇다. 폴더 규칙 1번이 **"모든 답변의 첫 줄은 예외 없이 `⟪YNC-RULES-V1⟫` 로 시작한다"** 였고, 명령 파일도 첫 줄을 요구했다. **둘 다 첫 줄을 원했고, 폴더 규칙이 이겼다.** 그리고 진 쪽은 조용히 사라졌다.

그래서 2단계 규칙의 마지막 줄을 넣었다 — "폴더 규칙이 첫 줄에 다른 마커를 요구하더라도, 그 줄 다음에 반드시 `⟪YNC-CLARIFY-V1⟫` 를 쓴다."

**여기서 얻을 것.** 확장 지점(스킬·명령·서브에이전트)을 만들 때 **그 폴더에 이미 무엇이 심겨 있는지 모르는 채로 형식을 요구하면 안 된다.** 형식을 요구할 거면 "다른 규칙과 어떻게 공존하는가"까지 써야 한다. 이건 `S2-5`의 인벤토리가 왜 필요한지에 대한 세 번째 답이다.

이 트랙에서 같은 종류의 충돌을 세 번 봤다.

| 어디서 | 무엇이 부딪혔나 |
|---|---|
| `S5-1` | `work/` 규칙 때문에 엉뚱한 폴더에 파일이 생겼다 |
| `S3-3` | 폴더 규칙의 마커가 루프 산출물에 섞였다 |
| 여기 | 폴더 규칙의 첫 줄이 명령의 첫 줄을 밀어냈다 |

**셋 다 내가 심은 규칙이 내 다음 작업을 방해한 것이다.** 하니스는 쌓을수록 서로 간섭한다.

### 명령이 답하지 말고 묻게 만드는 것이 요령이다

2단계 규칙의 "스스로 답하지 마라"가 핵심이다. 이걸 빼면 모델이 질문을 만들고 곧바로 자기가 답해 버린다. 그러면 결정을 모델이 한 것이 되고, 사람은 검토도 안 하고 넘어간다.

**명세 주도 개발에서 사람이 반드시 해야 하는 일은 "무엇이 옳은가"를 정하는 것이다.** 그건 코드에도 데이터에도 없다. 그래서 도구는 질문까지만 하고 멈춰야 한다.

### 슬래시 명령과 스킬의 차이

| | 스킬 (`S1-1`) | 슬래시 명령 (여기) |
|---|---|---|
| 발동 | 모델이 알아서 고른다 | 사람이 `/이름` 으로 부른다 |
| 자리 | `.claude/skills/*/SKILL.md` | `.claude/commands/*.md` |
| 인자 | 없음 (문맥에서 읽는다) | `$ARGUMENTS` |
| 쓸 때 | 조건이 맞으면 늘 | 내가 원할 때만 |

**인터뷰는 내가 원할 때만 하고 싶다.** 그래서 스킬이 아니라 명령으로 만들었다. 이 구분이 확장 지점을 설계할 때의 첫 질문이다 — **모델이 골라야 하는가, 사람이 불러야 하는가.**

### 막히면

| 증상 | 원인 | 조치 |
|---|---|---|
| `/clarify` 가 그냥 텍스트로 나온다 | 파일 위치가 틀렸다 | `.claude/commands/clarify.md` 확인 |
| 마커가 없다 | 폴더 규칙과 충돌했다 | 2단계 규칙 마지막 줄이 들어갔는지 확인 |
| 모델이 질문에 답까지 한다 | 규칙이 약하다 | "스스로 답하지 마라"를 맨 앞으로 옮긴다 |
| 질문이 구현 방법을 묻는다 | 같은 원인 | "무엇이 옳은지를 물어라"를 강조한다 |

### 클로드코드 안에서 하려면

**이 실습은 원래 창에서 하는 것이다.** `claude` 를 열고 `/clarify 내가 만들려는 것` 을 치면 질문이 나온다. 그 자리에서 답을 하면서 명세를 만들어 가는 것이 원래 쓰임새다. 창 안에서 `/help` 를 치면 지금 쓸 수 있는 슬래시 명령 목록에 `clarify` 가 보인다.

## S5-3. 수용 기준을 게이트에 연결한다

> 짝 | [C5-3](#lab-c5-3)

> 끝나면 | 명세를 안 읽고는 끝낼 수 없는 폴더

### 이 실습의 한 문장

명세의 수용 기준을 셸 시험으로 옮기고, 그 시험을 `Stop` 훅에 걸어 **명세를 만족할 때까지 끝내지 못하게** 한다.

### 단계

**3 · 채점기를 만든다** — 실패할 때 명세의 어느 절인지 알려 준다

```bash
cat > accept.sh <<'EOF'
#!/usr/bin/env bash
# spec.md 의 수용 기준을 실행 가능한 시험으로 옮긴 것.
[ -f duration.sh ] || { echo "duration.sh 가 없다"; exit 1; }
BAD=0; N=0
while IFS='|' read -r IN WANT WHY; do
  N=$((N + 1))
  GOT=$(bash ./duration.sh "$IN" 2>/dev/null)
  if [ "$GOT" != "$WANT" ]; then
    echo "FAIL  [$IN] -> [$GOT] (기대 [$WANT])   ← $WHY"; BAD=$((BAD + 1))
  fi
done < cases.txt
while IFS='|' read -r IN WHY; do
  N=$((N + 1))
  if bash ./duration.sh "$IN" > /dev/null 2>&1; then
    echo "FAIL  [$IN] 는 오류여야 한다   ← $WHY"; BAD=$((BAD + 1))
  fi
done < cases-err.txt
N=$((N + 1))
if bash ./duration.sh "" > /dev/null 2>&1; then
  echo "FAIL  빈 문자열은 오류여야 한다   ← 경계 사례 · 빈 문자열"; BAD=$((BAD + 1))
fi
echo "$((N - BAD))/$N 통과"
[ "$BAD" -eq 0 ]
EOF
chmod +x accept.sh
```

**4 · 게이트를 만든다** — `S2-4`와 같은 구조다

```bash
cat > .claude/hooks/accept-gate.sh <<'EOF'
#!/usr/bin/env bash
# Stop 훅: spec.md 의 수용 기준을 통과하지 못하면 끝내지 못한다.

echo "$(date +%H:%M:%S) 시도#$N rc=$RC | $(printf '%s' "$OUT" | tail -1)" >> .claude/gate.log

if [ "$RC" -eq 0 ]; then echo 0 > .claude/gate.count; exit 0; fi
if [ "$N" -ge 8 ]; then
  echo "$(date +%H:%M:%S) 상한 도달 — 통과시킴" >> .claude/gate.log
  echo 0 > .claude/gate.count; exit 0
fi
echo $((N + 1)) > .claude/gate.count

# 실패 항목을 그대로 실어 보낸다 (JSON 안에 넣으려고 따옴표·역슬래시만 지운다)
SAFE=$(printf '%s' "$OUT" | tr '\n' ' ' | tr -d '"\\')
printf '{"decision":"block","reason":"%s"}\n' \
  "spec.md 의 수용 기준을 아직 만족하지 않는다. 끝내지 말고 지금 폴더의 duration.sh 를 고쳐라. 하위 폴더를 만들지 마라. 화살표 뒤에 적힌 근거 절을 spec.md 에서 다시 읽어라. cases.txt 와 cases-err.txt 는 고치지 마라. 아래에 실패 항목이 다 있으니 명령을 따로 실행할 필요 없다. 실패 항목: $SAFE"
EOF
```

`S2-4`와 같은 이유로 **이 폴더의 권한을 여기서 다시 선언한다.**

**그래도 완전하지는 않다.** 이 문서를 만들며 여러 번 돌려 보니, 에이전트가 `./accept.sh` 를 직접 돌리려다 "테스트 실행 권한을 승인해주세요"에서 멈추는 일이 남아 있었다. 위쪽 `~/cc-step` 의 권한 규칙과 이 폴더의 규칙이 어떻게 합쳐지는지가 늘 예측대로는 아니다.

그래서 **명령을 못 돌려도 일이 되게** 만들었다. 4단계 차단 사유에 실패 항목 전부를 실어 보내고 "명령을 따로 실행할 필요 없다"를 명시한다. **판정기가 필요한 정보를 전부 돌려주면 에이전트가 도구를 쓸 필요가 없다.** 이게 권한 문제를 우회하는 가장 견고한 방법이다.

**나는 "명세는 읽지 말고 빨리 만들고 끝내라"고 했다.** 에이전트는 그렇게 했다. 그리고 끝내지 못했다.

로그의 숫자가 올라가는 것을 보라. 9 → 14 → 16 → 17. **게이트는 매번 "무엇이 왜 틀렸는지"를 근거 절과 함께 돌려준다.** 그래서 에이전트가 명세를 읽으러 갈 수밖에 없다.

**이게 명세 주도 개발이 실제로 작동하는 방식이다.** 명세를 문서로 두면 아무도 안 읽는다. 명세를 **완료 조건**으로 만들면 반드시 읽는다.

### 게이트 로그의 앞 세 줄 — 또 그 폴더 규칙이다

7단계를 돌리면 `gate.log` 앞부분이 이렇게 나오기도 한다.

```
01:30:30 시도#0 rc=1 | duration.sh 가 없다
01:30:36 시도#1 rc=1 | duration.sh 가 없다
01:30:40 시도#2 rc=1 | duration.sh 가 없다
01:31:14 시도#3 rc=1 | 13/17 통과
```

**세 번이나 "파일이 없다"가 나온 이유가 있다.** 에이전트가 첫 시도에 파일을 만들긴 했는데, `~/cc-step/work/duration.sh` 에 만들었다. `S2-2`에서 심은 **"파일은 `work/` 아래에만 만든다"** 규칙 때문이다. 여기는 이미 `work/sdd/gated` 안인데도 규칙을 문자 그대로 적용해 버렸다.

그래서 7단계 프롬프트에 **"지금 이 폴더에 만들어라. 하위 폴더를 만들지 마라"** 를 넣었고, 차단 사유에도 같은 문장을 넣었다.

**이 트랙에서 그 폴더 규칙 하나가 네 번째로 사고를 냈다.** `S5-1`, `S3-3`, `S5-2`, 그리고 여기다. 하니스를 설계할 때 기억할 것 — **규칙은 심는 순간이 아니라 몇 주 뒤 다른 작업에서 비용을 청구한다.** 그리고 그 청구서는 "왜 안 되지?" 하며 30분을 태우는 형태로 온다.

### 근거 절을 시험에 적어 둔 이유

2단계 표의 세 번째 칸(`기능 요구사항 · 대문자` 같은 것)은 사람을 위한 것이 아니라 **에이전트를 위한 것**이다.

실패 메시지가 "1H30M 이 틀렸다"이면 에이전트는 추측으로 고친다. "1H30M 이 틀렸다 ← 기능 요구사항 · 대문자"이면 명세의 그 줄을 읽으러 간다. **판정기가 명세를 가리키게 만들면, 판정기가 명세를 읽히게 만든다.**

그리고 이 칸이 있으면 반대 방향도 가능해진다 — 명세의 어느 줄이 시험으로 옮겨지지 않았는지 세어 볼 수 있다. 1단계에서 항목 수를 센 것이 그 준비다.

**9 · 절을 구분하는 검사기를 만든다**

```bash
cat > drift.sh <<'EOF'
#!/usr/bin/env bash
# 절을 구분하는 표류 검사기. 약속한 절과 금지한 절을 따로 본다.
awk '/^## 범위 밖/ {exit} {print}' spec.md > .promised.txt
awk '/^## 범위 밖/ {f = 1} f'        spec.md > .excluded.txt

BAD=0
while IFS=';' read -r NAME PROBE PAT; do
  if bash ./duration.sh "$PROBE" > /dev/null 2>&1; then IN_CODE=1; else IN_CODE=0; fi
  if grep -qE "$PAT" .promised.txt; then PROMISED=1; else PROMISED=0; fi
  if grep -qE "$PAT" .excluded.txt; then EXCLUDED=1; else EXCLUDED=0; fi

  if   [ "$IN_CODE" = 1 ] && [ "$EXCLUDED" = 1 ]; then
    echo "CONFLICT  $NAME — 명세가 '범위 밖' 이라 한 것이 코드에서 동작한다"; BAD=$((BAD + 1))
  elif [ "$IN_CODE" = 1 ] && [ "$PROMISED" = 0 ]; then
    echo "DRIFT     $NAME — 코드에서 되는데 명세가 약속하지 않았다"; BAD=$((BAD + 1))
  elif [ "$PROMISED" = 1 ] && [ "$IN_CODE" = 0 ]; then
    echo "MISSING   $NAME — 명세가 약속했는데 코드에서 안 된다"; BAD=$((BAD + 1))
  else
    echo "ok        $NAME"
  fi
done < features.txt
echo
echo "문제 ${BAD}건"
[ "$BAD" -eq 0 ]
EOF
chmod +x drift.sh && ./drift.sh; echo "→ exit $?"
```

**요청한 두 기능 중 하나만 붙었다.** `1d` 는 86400을 내고, `1h 30m` 은 여전히 오류다. 이 실행에서 에이전트는 일 단위만 넣고 공백 허용은 넣지 않았다.

왜 그랬는지는 알 수 없다 — 게이트가 켜져 있으니 기존 17개를 깨지 않는 쪽으로 움직였을 수도 있고, 그냥 하나를 흘렸을 수도 있다. **중요한 것은 내가 시킨 것과 실제로 들어간 것이 다르다는 사실을 게이트가 알려 주지 않았다는 점이다.** 게이트는 `rc=0` 한 줄만 남겼다. 9단계의 검사기가 없었으면 이 차이를 아무도 몰랐을 것이다.

`CONFLICT` 가 두 건 나오는 실행도 있다. 몇 건이냐는 중요하지 않고, **0건이 아니라는 것**이 중요하다.

### 세 가지를 한꺼번에 배운다

**첫째, 게이트는 표류를 못 잡는다.** 4단계를 보라. 게이트는 첫 시도에 `17/17 통과` 로 통과시켰다. 범위 밖 기능이 들어왔는데도.

이유는 단순하다. **테스트는 있는 것만 검사한다.** 명세가 약속한 항목이 동작하는지는 확인하지만, **명세가 금지한 것이 코드에 들어왔는지는 확인하지 않는다.** 수용 기준을 아무리 촘촘히 써도 초과 표류는 원리적으로 안 잡힌다.

**둘째, 순진한 검사기는 정반대로 판정한다.** 7단계가 `표류 0건` 을 냈다. 코드에서 `1d` 가 동작하는 것은 맞게 봤는데(`코드 1`), 명세 전체에서 "일(" 을 찾았더니 있었으므로(`명세 1`) 약속된 것으로 판정했다. **금지 문장을 약속 문장으로 읽은 것이다.**

이건 실무에서 아주 흔한 종류의 버그다. 검사기가 "찾았다/못 찾았다"만 보면 **찾은 자리의 의미**를 놓친다.

**셋째, 코드를 읽지 않고 돌려 봐서 잡았다.** 9단계의 검사기는 `duration.sh` 를 한 글자도 안 읽는다. `bash ./duration.sh 1d` 를 돌려서 성공하면 그 기능이 있는 것으로 본다. **정규식으로 코드를 훑는 것보다 훨씬 정확하다.** 코드가 어떻게 짜였든 동작이 답이기 때문이다.

**다만 한계가 있다.** 돌려 볼 수 없는 표류는 못 잡는다 — 아무도 안 부르는 함수가 하나 추가됐다면 이 검사기는 조용하다. 그건 코드를 읽어야 한다. **검사기는 하나로 충분한 적이 없다.**

### 표류가 나쁘기만 한 것은 아니다

일 단위 지원이 실제로 필요할 수도 있다. **표류가 잘못이라는 게 아니라, 표류가 조용한 것이 잘못이다.**

`CONFLICT` 가 떴을 때 할 일은 둘 중 하나다.

1. 기능이 필요하다 → **명세를 고친다.** `## 범위 밖` 에서 빼서 `## 기능 요구사항` 으로 올리고, 수용 기준과 시험 항목을 추가한다.
2. 기능이 필요 없다 → **코드를 되돌린다.** 10단계가 그것이다.

**둘 다 사람이 정한다.** 검사기는 결정하지 않는다. 결정할 자리를 만들 뿐이다. 그게 없으면 명세와 코드는 6개월 만에 남남이 된다.

## 이해도 점검

**1. 이 트랙이 `python3 -c` 를 쓰지 않고 `grep -o` 로 JSON 을 읽는다. 이 방식의 한계는 무엇인가?**

답: 중첩과 이스케이프를 모른다. `grep -o '"result":"[^"]*"'` 는 문자열 안에 이스케이프된 따옴표가 있으면 거기서 잘리고, 같은 이름의 필드가 여러 겹에 있으면 전부 뽑아 온다(`S0-2`의 `input_tokens` 가 `usage` 와 `iterations` 양쪽에 있는 것이 그 예다). 그래서 `head -1` 이나 `sort -u` 로 다듬어야 한다. **찾기이지 파싱이 아니다.** 값이 단순하고 위치가 예측 가능할 때만 쓴다. 그 조건이 깨지면 `jq` 나 파이썬으로 올라가야 한다. (S0-2, S2-3)

**2. `grep -c` 가 `0` 을 출력하면서 종료 코드 1 을 내는 것이 왜 편리한가?**

답: 판정과 표시가 한 번에 되기 때문이다. 화면에는 개수가 보이고, `&&` 나 `if` 로 이으면 그대로 조건이 된다. `S2-4`의 `run_tests.sh` 마지막 줄 `[ "$BAD" -eq 0 ]` 도 같은 원리다 — 스크립트의 종료 코드가 곧 판정이다. 다만 `set -e` 를 켠 스크립트 안에서는 `grep -c` 가 0을 낼 때 스크립트가 통째로 멈추므로 `|| true` 를 붙이거나 `set +e` 로 둬야 한다. (S1-1, S2-4)

**3. `S1-3`에서 MCP 서버 코드를 주지 않고 명세만 준 이유는?**

답: 앞으로 실제로 하게 될 일이 그것이기 때문이다. 커넥터가 필요할 때 사람이 손으로 쓰지 않는다. 명세를 주고 시킨다. 그래서 필요한 능력은 파이썬이 아니라 **명세를 정확히 쓰는 능력**이고, 그 명세에 `ensure_ascii=False` 나 경로 탈출 차단 같은 항목이 빠지면 그대로 빠진 채 만들어진다. 실패했을 때 오류를 붙여넣고 고치게 하는 것까지가 실습이다. (S1-3)

**4. `S1-4`에서 haiku 와 sonnet 의 점수가 거의 같게 나왔다. 여기서 내릴 결론과 내리면 안 되는 결론은?**

답: 내릴 결론은 "**형식이 명확히 정의된 과제에서는** 작은 모델로 충분하다"이다. 내리면 안 되는 결론은 "sonnet 은 필요 없다"이다. 이 시험은 `S1-1`의 스킬이 형식을 다섯 개로 못 박아 둔 과제였다. 판단이 필요한 과제(`S1-3`의 아홉 가지 요구사항을 동시에 만족하는 코드, `S5-1`의 명세 구현)에서는 차이가 난다. **모델을 키우기 전에 과제를 좁혀라**가 옳은 순서다. (S1-4)

**5. `S2-2`에서 첫 줄 마커 규칙(1번)보다 `work/` 규칙(2번)이 더 잘 지켜지는 이유는?**

답: 판단의 횟수가 다르다. `work/` 규칙은 파일을 쓰는 도구를 부르는 **한 번의 순간**에 결정된다. 첫 줄 마커는 답변을 생성하는 **매 순간의 습관**이다. 구조적인 규칙일수록 잘 지켜진다. 그래서 진짜로 지켜야 하는 것은 `CLAUDE.md` 에 쓰지 말고 훅이나 권한 규칙으로 내려야 한다. `CLAUDE.md` 는 강제가 아니라 지시이고, 지시는 확률적이다. (S2-2)

**6. `S2-3`에서 훅 스크립트 파일을 치웠는데 오류가 안 났다. 왜 위험한가?**

답: 설정에는 훅이 등록돼 있는데 파일이 없으면 **조용히 통과**된다. 그래서 방어가 사라진 것을 아무도 모른다. 훅 스크립트를 `.gitignore` 에 넣거나 팀원이 `chmod +x` 를 안 하면 그 사람의 컴퓨터에는 방어가 없고, 그 사실이 어디에도 드러나지 않는다. 훅은 반드시 저장소에 함께 커밋하고, `S2-5`의 감사처럼 살아 있는지 확인하는 절차가 있어야 한다. (S2-3, S2-5)

**7. `S3-2`의 관측 스크립트에 `date` 를 넣으면 무슨 일이 일어나는가?**

답: 매 틱마다 해시가 달라져 억제가 한 번도 일어나지 않는다. 게이트가 있는데도 절약이 0이 되고, 겉보기에는 정상으로 보인다(로그에 "변화"만 계속 쌓인다). 관측 출력에는 시각·난수·프로세스 ID가 들어가면 안 되고, 목록은 반드시 정렬해야 하며, 관측이 파일을 만들거나 고치면 자기가 자기를 깨우게 된다. (S3-2)

**8. `S3-3`에서 상태를 `state.json` 대신 `queue.txt` + `cursor.txt` 로 나눈 이유와, 그 선택의 대가는?**

답: 이유는 셸의 기본 명령만으로 읽고 쓸 수 있고(`sed -n '3p'`, `echo 4 >`), 상태가 눈에 보인다는 것이다. 대가는 **원자성이 없다는 것**이다. 두 파일을 따로 갱신하므로 그 사이에 죽으면 목록과 커서가 어긋난다. JSON 하나면 한 번의 쓰기로 끝난다. 상태가 복잡해지거나 동시 실행이 생기면 파일 하나로 합치고 임시 파일 + `mv` 로 원자적으로 갱신해야 한다. (S3-3)

**9. `--max-budget-usd 0.002` 를 걸었는데 0.013 달러가 나갔다. 버그인가?**

답: 아니다. 예산은 **턴 사이에** 검사된다. 진행 중인 턴을 중간에 잘라내지 않으므로 한 턴이 예산을 넘기면 그 턴이 끝난 뒤에 중단된다. 상한은 정확한 천장이 아니라 폭주를 멈추는 브레이크다. 그리고 `is_error: true` 로 끝나므로 자동화에서는 그 잡이 실패로 처리되고, 재시도 로직이 그대로 돌면 또 예산까지 쓰고 실패한다. (S3-4)

**10. `S4-2`에서 `Read → Read` 나 `Bash → Bash` 같은 전이가 많은 도구는 무엇을 뜻하는가?**

답: 그 도구가 한 번에 필요한 것을 못 줬다는 뜻이다. 에이전트가 헤맨 자리이고, **도구 개선의 최우선 순위**다. 반대로 `list_notes → read_note` 처럼 항상 붙어 다니는 쌍은 두 도구가 하나여야 한다는 신호다. 왕복이 줄면 문맥과 비용이 함께 준다. 그리고 이 분석에는 모델을 한 번도 안 부른다 — 기록은 이미 디스크에 있다. (S4-2)

**11. `S4-3`의 인용 대조에서 "의미상 같으면 통과"로 하면 안 되는 이유 두 가지는?**

답: 첫째, 의미 판정에는 다시 LLM 이 필요하고 그러면 판정자가 판정 대상만큼 복잡해진다. 판정자의 오류는 아무도 검증할 수 없다. 검증기는 검증 대상보다 단순해야 한다. 둘째, 환각의 흔한 형태는 완전한 창작이 아니라 **미세한 변형**이다. "도입하지 않는다"에서 "않는다"가 빠지면 정반대가 되는데, 의미 판정기는 이걸 비슷하다고 볼 수 있고 `grep -qF` 는 반드시 잡는다. 인용이 자꾸 실패하면 고칠 곳은 검증기가 아니라 프롬프트다. (S4-3)

**12. `S5-3`의 게이트는 `S5-4`의 표류를 잡지 못했다. 왜인가? 그리고 잡으려면 무엇이 더 필요한가?**

답: **테스트는 있는 것만 검사한다.** 명세가 약속한 항목이 동작하는지는 확인하지만, 명세가 금지한 것이 코드에 들어왔는지는 확인하지 않는다. `S5-4`에서 일 단위와 공백 허용을 넣었는데 수용 기준 17개가 전부 통과한 것이 그 증거다. 잡으려면 **코드에서 명세로 거꾸로 훑는 별도의 검사기**가 필요하고, 그 검사기는 명세의 절을 구분해서 약속한 절과 금지한 절을 따로 봐야 한다. 한 덩어리로 보면 금지 문장을 약속 문장으로 읽는다. (S5-3, S5-4)

**13. `S5-4`의 검사기가 코드를 정규식으로 훑지 않고 실제로 실행해서 판정하는 것의 장점과 한계는?**

답: 장점은 코드가 어떻게 짜였든 **동작이 답**이라는 것이다. `86400` 이라고 썼든 `24*3600` 이라고 썼든 `1d` 를 넣어 보면 안다. 정규식은 구현 방식이 조금만 달라도 놓친다. 한계는 **돌려 볼 수 없는 표류는 못 잡는다**는 것이다. 아무도 안 부르는 함수가 추가됐거나, 로그를 외부로 보내는 코드가 들어왔다면 이 검사기는 조용하다. 검사기는 하나로 충분한 적이 없다. (S5-4)

**14. `S2-4`와 `S5-3`의 작업 폴더가 자기 `permissions` 를 다시 선언하는 이유는? 그리고 그것만으로 왜 부족한가?**

답: 두 폴더는 `~/cc-step` 안에 있고, 위쪽에는 `S2-1`·`S2-3`에서 만든 **특정 명령만 허용하는** 권한 규칙이 있다. 그 상태에서 에이전트가 `./run_tests.sh` 나 `./accept.sh` 를 돌리려 하면 승인을 기다리다 멈추는데, `-p` 모드에는 승인해 줄 사람이 없다. 그래서 작업 폴더가 자기에게 필요한 권한을 스스로 선언해야 한다. **다만 그것만으로도 부족했다** — 상위 규칙과의 병합 결과가 늘 예측대로는 아니었다. 그래서 더 견고한 대응을 같이 넣었다: **차단 사유에 실패 항목 전부를 실어 보내고 "명령을 따로 실행할 필요 없다"를 명시한다.** 판정기가 필요한 정보를 다 돌려주면 에이전트는 도구를 쓸 필요가 없고, 권한 문제 자체가 사라진다. (S2-4, S5-3)

**15. 이 트랙과 C 트랙을 둘 다 남긴 이유는?**

답: 쓰임이 다르다. S 트랙은 **따라 하기** 위한 것이다 — 한 명령, 한 확인, 다음. C 트랙은 (1) 강사가 수업 전에 환경을 한 번에 점검할 때, (2) 학생이 막혔을 때 정답 전체를 볼 때, (3) 같은 일을 파이썬으로 어떻게 하는지 비교할 때 쓴다. 그리고 자동 검증에는 한방 스크립트가 훨씬 유리하다. **가르치기 좋은 형태와 검증하기 좋은 형태는 다르다.** (전체)

## 실습 과제

**과제 1. 이어하기 루프를 커서에서 집합으로 바꾼다.**

`S3-3`의 `cursor.txt` 는 숫자 하나로 진행을 관리한다. 그래서 새로 넣은 `inbox/004.txt` 를 영원히 무시했다. 이걸 고친다. **셸만 쓴다.**

- `cursor.txt` 를 버리고 `done.txt`(처리한 파일 이름 목록)를 쓴다.
- 매 틱마다 `ls -1 inbox/` 를 다시 읽고, `done.txt` 에 없는 것 중 **가장 앞의 하나**만 처리한다. `comm -23` 이나 `grep -vxFf` 를 쓰면 한 줄로 된다.
- 처리에 성공했을 때만 `done.txt` 에 추가한다. 실패하면 넣지 않는다(다음 틱에 다시 시도한다).
- 실패를 어떻게 감지할지 먼저 정한다. `claude -p` 의 종료 코드인가, 출력이 비었는지인가, 둘 다인가.
- 새 편지를 하나 넣고 다섯 틱을 돌려, 새 편지가 처리되고 기존 편지는 재처리되지 않는 것을 확인한다.

**왜 이게 과제인가.** 커서는 "어디까지 왔는가"를 말하고 집합은 "무엇을 했는가"를 말한다. 목록이 변하지 않는다면 둘은 같지만, 현실의 목록은 변한다. **실패 시 되돌리기**까지 넣는 것이 핵심이다 — 그게 없으면 실패한 항목이 조용히 사라지고, 몇 주 뒤에야 알게 된다.

**과제 2. `S4-3`의 대조기를 `S2-4`의 게이트에 꽂는다.**

지금 `check.sh` 는 사람이 손으로 돌린다. 이걸 자동화한다.

- 새 작업 폴더를 만들고 `source.md` 를 둔다.
- `Stop` 훅에 `check.sh` 를 걸어, 근거 없는 주장이 하나라도 있으면 끝내지 못하게 한다.
- 차단 사유에 **어느 주장이 왜 실패했는지**를 넣는다. `S5-3`의 근거 절 표기를 참고한다.
- 에이전트에게 "source.md 를 요약해서 pairs.txt 에 `주장|인용` 형식으로 써라"만 시키고, 몇 번의 시도 끝에 통과하는지 `gate.log` 로 센다.
- **상한을 반드시 넣는다.** 없으면 무한 루프다.

**왜 이게 과제인가.** 검증기가 있어도 사람이 돌려야 한다면 결국 안 돌린다. 판정기를 완료 경로에 꽂는 것까지가 하나의 작업이다. 그리고 이 과제를 하면 `S2-4`(코드 시험), `S5-3`(수용 기준), 이 과제(근거 검증)가 **모두 같은 구조**라는 것이 보인다.

**과제 3. 한 실습을 골라 파이썬 버전과 셸 버전을 비교한다.**

이 트랙과 C 트랙에서 같은 번호의 실습을 하나 고른다. `S4-2`/`C4-2`(발자국 그래프)나 `S5-4`/`C5-4`(표류 검사)를 권한다.

- 두 구현이 **같은 입력에 대해 같은 답을 내는지** 확인한다. 다르면 왜 다른지 찾는다.
- 각각 몇 줄인지, 몇 개의 개념(파일 읽기·정규식·자료구조·정렬)을 알아야 읽을 수 있는지 센다.
- 각 버전이 **깨지는 조건**을 하나씩 찾는다. 셸 버전은 어디서 깨지고 파이썬 버전은 어디서 깨지는가.
- 셋을 표로 정리하고, "이 일에는 어느 쪽이 맞다"를 한 문단으로 쓴다.

**왜 이게 과제인가.** 도구 선택은 취향이 아니라 판단이다. 셸은 파이프로 잇는 일과 파일을 세는 일에 강하고, 중첩된 자료와 오류 처리에 약하다. 그 경계를 **직접 재 본 사람**과 들어서 아는 사람은 다르다. 그리고 이 강의에서 배운 것 중 실무에서 가장 자주 쓰게 될 판단이 이것이다 — **이 일을 사람이 짤 것인가, 에이전트에게 시킬 것인가, 아니면 셸 한 줄로 끝낼 것인가.**
